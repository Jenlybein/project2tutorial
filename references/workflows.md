# Workflow 路由（先判断该走哪一条流水线）

判据不是用户嘴上说了什么词，而是两件事：**他手里已经有什么**、**他最后要拿去做什么**。
手里有源码、要能复现 → A；只想看懂结构 → B；已有架构说明、只缺文档 → C；只有一堆素材、要成文 → D。
四条流水线共用同一批角色与同一套输出规范，差别只在起点与终点。

## 预设 Workflow

### Workflow A：完整拆解 + 全教程（默认）
- **触发条件**："拆解这个项目并写成教程""把这个仓库讲透""我要看懂并复现它"
- **Phase 编排**：Phase 0 → 0.5（串行）→ 1（并行，UI 按需）→ 2（串行）→ 2.5（串行）→ 3（并行）→ 4（串行）→ 5（并行，三人）→ 5.5（串行，面试与简历）→ 6

### Workflow B：只要架构
- **触发条件**："看不懂这个项目的结构""帮我理一下模块划分""它整体怎么跑起来的"
- **Phase 编排**：Phase 0 → 0.5（串行）→ 1（并行，UI 按需）→ 2（串行）→ 2.5（可选，用户要数字与边界时才做）→ 6（仅输出架构文档）

### Workflow C：已有架构，只要教程
- **触发条件**：用户已提供架构说明，要求产出章节文档或复现指引
- **Phase 编排**：跳过 1、2；有源码则先 Phase 0.5；有源素材则先 Phase 2.5 → Phase 3（并行）→ 4（串行）→ 5（并行，三人）→ 6

### Workflow D：只要章节文档
- **触发条件**："把这些材料整理成多章 Markdown""按模块分章节"
- **Phase 编排**：Phase 0.5（素材底座：文档清单 + 主题聚类 + 引用锚点）→ 2.5（若用户给了成捆素材）→ 3（仅 longform-writer）→ 5（longform-writer + source-auditor）→ 6

> **面试与简历章只在 Workflow A 里默认产出。** B/C/D 的产物不足以支撑完整的项目叙述，不硬加。用户在任何 Workflow 里明确说要准备面试或写简历时，补一个 Phase 5.5；反之用户明确说"只要技术文档、不要职场向内容"时，A 里也可以跳过 5.5——**跳过要在汇报里说一声，别悄悄省掉。**

## 单 agent 直调路由表

| 问法类型 | 直接调谁 |
|---------|---------|
| 只想看整体或某模块的运行架构 | software-architect |
| 想看某段代码怎么跑起来 / 数据怎么流转 | senior-engineer |
| 想看界面、交互、视觉规范 | ui-designer |
| 想把一堆材料整理成长文档 / 给长文改稿 | longform-writer |
| 想要教程文案、示例、叙述表达、实操指引 | content-creator |
| 想查漏：源素材都吸收了吗 / 数字对不对得上 / 有没有断链 | source-auditor |
| 想把这个项目写进简历 / 准备面试怎么讲 | content-creator（产出后必须交 source-auditor 核一遍表述可溯源） |
| 综合性问题（拆解 + 文档 + 教程） | 走 Workflow A |

## 降级与裁剪（小项目别硬套全流程）

- **小项目**（十几个文件、无界面、单一入口）：Phase 1 只拉 engineer 一人做执行路径 + 架构合写；Phase 2 与 0.5 可合并；Phase 3 一人写完全书。流程的价值是防错，不是仪式。
- **无界面项目**：不拉 `ui-designer` 做界面分析；图量大时才拉他一次，只产《配图视觉规范》。
- **无源码、只重组素材**：跳过 0.5 与 2 之外的源码类工作，底座改成「素材清单 + 主题聚类 + 引用锚点」（Workflow D 的形态）。
- **用户只要架构**：走 B，2.5 只在用户关心数字与边界时做；不要顺手把教程也写出来——多出来的东西会稀释交付。
- **面试简历章**：只在 A 里默认产出；跳过时必须在汇报里说一声，不能悄悄省掉。

## 成本预期（据此决定要不要先跟用户对齐）

A 是重活：约 10 个阶段、6 个角色、十几到几十个子 agent 派工（章节多时要按批次继续派）。开工前用一句话告诉用户「这轮要跑哪些阶段、大概多久、产出长什么样」，比闷头跑完再解释便宜得多。
