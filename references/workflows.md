# Workflow 路由（档位序列的唯一真相源）

判据是三件事：**用户手里已有什么**、**最后要拿去做什么**、**项目有多大**。有源码且要复现 → A；只想看懂结构 → B；已有架构说明只缺文档 → C；只有素材要成文 → D。**A 档再按规模自动分 A-lite / A-全量，不要默认跑全量。**

四条流水线共用同一批角色与同一套输出规范，差别只在起点与终点。

**四条都以 Phase 0（需求与素材确认）开场**，下表写的是 Phase 0 之后的序列。每个阶段的输入、产出、验收标准与交接规则见 `references/pipeline.md`；本文件只负责裁序列，不重复阶段细则。

| 档位 | 触发 | Phase 0 之后的序列 |
|---|---|---|
| **A 完整拆解 + 全教程** | 拆解项目并写成教程、把这个仓库讲透、看懂并复现它 | **A-全量**：0.5 → 1（UI 按需）→ 2 → 2.5 → 2.8 → 3（分批）→ 4 → 5 → 5.5 → 6；**A-lite** 合并 0.5/1/2 并按「A 档规模分流」裁剪角色 |
| **B 只要架构** | 看不懂结构、理清模块划分、整体怎么跑起来的 | 0.5 → 1（UI 按需）→ 2 →（2.5 仅当用户关心数字与边界）→ 6 |
| **C 已有架构只要教程** | 用户已提供架构说明，要章节文档或复现指引 | （有源码则 0.5）→ **2.5（必做**：有源素材时对账，否则仍建数字账本**）** → 2.8 → 3 → 4 → 5 → 6 |
| **D 只要章节文档** | 把一堆按专题写的材料整理成多章 Markdown | 0.5（素材底座）→ 2.5 → 2.8 → 3（仅主笔）→ 5（主笔 + 审计）→ 6 |

> **A/C/D 里 2.5 是 2.8 的上游**（B 不过 2.8）。C/D 跳过 Phase 2 时，2.8 的口径来源不是 canon 表：C 用用户给的架构说明（缺 canon 时用 2.5 的「前后矛盾清单」兜底），D 用 2.5 的「前后矛盾清单」+ 源素材里的命名与定义。逐档输入见 `references/pipeline.md` 的 Phase 2.8。

> **2.8 别省。** 它只有两个文件、半小时成本，却决定后面几百处术语和重复是否会发生。跳过它，Phase 5 就得用人眼全库扫一遍还债。凡是会写章节正文的档位（A / C / D）都要过 2.8；B 只出架构文档，不过。

> **面试与简历（5.5）只在 A 默认产出。** B/C/D 的产物不足以支撑完整的项目叙述，不硬加；用户明确要准备面试或写简历时补一个 5.5。反过来，A 里用户明确说「只要技术文档、不要职场向内容」时可以跳过——**跳过要在汇报里说一声，别悄悄省掉。**

## A 档规模分流（Phase 0 必做，默认 A-lite）

**Phase 0 确认完五件事后，主理人按项目规模直接落档，把结果写进 Phase 序列通报；不把「要不要裁」留给后面的自觉。**

| 判据 | 落档 |
|---|---|
| 源码 ≲ 20 个文件、单一入口、无界面、预计章节 ≲ 12 篇 | **A-lite（默认）** |
| 多模块 / 有界面 / 章节多 / 用户明确要求多人分工 | **A-全量** |

两条边界：拿不准就按 A-lite 跑，中途发现章节明显超量再升档，并补通报；用户明确要求「每个角色都拉齐」时直接 A-全量。

**两档共享的全局规则（不要重复计收益）**：① 2.5 / 2.8 保留两次派工，有依赖、不合并；② **写作期代码抽检只在第一批做一次**做早期纠偏，其余可执行性交 Phase 5 全量核对（相对旧版「每批后抽检」两档都省 4–6 次）；③ 派工输入按 `references/pipeline.md` 的三层裁剪，架构定稿只在第一批整篇读。

| 项 | A-全量 | **A-lite** | A-lite 额外省 |
|---|---|---|---|
| 0.5 / 1 / 2 | 三次派工（+ UI 按需 1 次） | **合并为一次**：`senior-engineer` 出「底座 + 执行路径 + 架构结论」合稿（仍需含 canon 口径冻结表一节） | 2–3 次 |
| 2.5 / 2.8 | 2 次 | 2 次 | — |
| 3 写作 | 2 写手 × 5–7 批 = 10–14 次 | **单写手 × 2–3 批 = 2–3 次**（`longform-writer` 一人写全套四件套；`00` 仍独立成篇） | 8–11 次 |
| 3 抽检 | 1 次（全局规则） | 1 次（全局规则） | — |
| 4 / 5 | 1 + 3 次 | **1 + 2 次**：Phase 5 只拉 `senior-engineer`（可执行）+ `source-auditor`（忠实与完整），**不拉写手本人** | 1 次 |
| 5.5 | 2 次（写 + 核） | **1 次**：`content-creator` 写；`source-auditor` 在 Phase 5 顺手产「素材落点索引」，主理人合稿与 5.5 按索引机械核对，只有无落点 / 口径冲突才派 auditor 裁决 | 1 次 |
| 合计（不含主理人） | **23–28 次** | **10–11 次**（5.5 有争议时 +1） | 13–17 次，约 55–60% |

> 以上是常规情况的预算。**两个显式例外，通报时要说一声**：① Phase 5 合稿改动量大、主理人按章节另派写作子 agent 落盘时，每批 +1 次；② A-lite 中途发现章节明显超量升回 A-全量时，按 A-全量重新计。

**防线补偿（单写手不能自己查自己）**：A-lite 的 Phase 5 刻意不拉 `longform-writer`，改由工程师 + 审计两向检查；表达质量靠 `glossary.md` / `ownership.md`、自检 12 条与 `audit_teardown.py` 兜底。**这是明确的防线降级，必须在 Phase 0 通报里写明「本项目走 A-lite，单写手 + 换人双查」**，用户要求多人分工时立即升回 A-全量。

## 单 agent 直调路由表

| 问法类型 | 直接调谁 |
|---------|---------|
| 只想看整体或某模块的运行架构 | software-architect |
| 想看某段代码怎么跑起来 / 数据怎么流转 | senior-engineer |
| 想看界面、交互、视觉规范 | ui-designer |
| 想把一堆材料整理成长文档 / 给长文改稿 | longform-writer |
| 想要教程文案、示例、叙述表达、实操指引 | content-creator |
| 想查漏：源素材都吸收了吗 / 数字对不对得上 / 有没有断链 | source-auditor |
| 想把这个项目写进简历 / 准备面试怎么讲 | content-creator（产出后必须交 source-auditor 核一遍表述可溯源） |
| 综合性问题（拆解 + 文档 + 教程） | 走 Workflow A |

## 降级与裁剪（小项目别硬套全流程）

- **小项目**：按上面的「A 档规模分流」自动走 A-lite，不再作为可选建议；合并与换人双查规则以该表为准。
- **无界面项目**：不拉 `ui-designer` 做界面分析；图量大时才拉他一次，只产《配图视觉规范》。
- **无源码、只重组素材**：走 D，底座改成「素材清单 + 主题聚类 + 引用锚点」，跳过源码类分析。
- **用户只要架构**：走 B，2.5 只在用户关心数字与边界时做；不要顺手把教程也写出来——多出来的东西会稀释交付。
- **面试简历章**：只在 A 里默认产出；跳过时必须在汇报里说一声，不能悄悄省掉。

## 成本预期（据此决定要不要先跟用户对齐）

A-全量是重活：11 个阶段、6 个角色、23–28 次子 agent 派工；**A-lite 约 10–11 次**。开工前用一句话告诉用户「这轮走 A-lite / A-全量、跑哪些阶段、大概多久、产出长什么样」，比闷头跑完再解释便宜得多。其余档位按上表裁掉阶段即可，不必先报时长。
