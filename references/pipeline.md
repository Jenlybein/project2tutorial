# 流水线（pipeline）

一条路，七步。每一步都按 **输入 → 内部运作 → 输出** 组织：输入决定它能看到什么，内部运作是它该做的事，输出是下一阶段的输入。**上一步没落盘，下一步不许开工。**

交付目录：`<项目名>-拆解教程/`；工作区：`<项目名>-拆解教程/.work/`（中间产物，不交付、不进 README、脚本跳过）。

## 交接约定

1. **完整正文必须落盘。** 子 agent 只回传交接（≤10 行：写了哪些文件、关键判断、未决项），不靠对话传正文——摘要进上下文，细节就丢了。
2. **下一阶段的输入是文件路径 + 一句「整篇读完再开工」**，不是摘要、不是节选。列进 prompt 的每一份都要整篇读完。
3. **同一阶段并行的成员，写范围必须不重叠。** 重叠就改串行，没有别的办法。

## 阶段产物

| 阶段 | 谁 | 产出（`.work/`） |
|---|---|---|
| 0 需求确认 | 主理人 | 五件事的答案，写在对话里 |
| 1 代码地图 | Evan Trace | `01-map/codemap.md` |
| 2 架构认知 | Atlas Vaughn | `02-arch/layers.md`、`02-arch/modules.md`、`02-arch/flows.md` |
| 3 模块深挖 | Atlas Vaughn（+ Evan Trace） | `03-deepdive/<模块>.md` |
| 4 写前冻结 | Vera Cross | `freeze/glossary.md`、`freeze/ownership.md` |
| 5 写作 | Lena Quill + Cleo Spark | 章节正文 + `assets/` + `05-authoring/toc.md` |
| 6 交付闸门 | 主理人 + Vera Cross | 修正入稿、`README.md`、`06-review/checklist.md` |

---

## Phase 0：需求确认（主理人）

**输入**：用户的一句话需求。

**内部运作**：问清五件事，缺项就问，不替用户决定：

1. 项目来源：本地路径 / 仓库 URL / 压缩包 / 素材目录
2. 目标读者：新手 / 有基础的开发者 / 架构研究者
3. 教程深度：只要架构讲透，还是要能跟着复现
4. 输出目录：默认当前工作目录下的 `<项目名>-拆解教程/`
5. 素材范围：有多少篇、按什么方式组织

**输出**：五件事的答案 + 一句通报「下一步先去读代码地图」。

**为什么先问**：读者决定术语解释的深度，深度决定后面要不要写复现内容，素材范围决定结尾怎么对账——这四件事任何一件猜错，后面整本都要返工。

---

## Phase 1：代码地图（Evan Trace）

**输入**：项目源码位置；素材型输入则换成素材目录。

**内部运作**：

1. 列出文件树（只到能看出结构的三层，不要贴全量文件列表）
2. 找入口：进程/服务/CLI 从哪启动，几个入口
3. 抽依赖：包管理文件、构建配置、容器与 CI 里读出依赖及精确版本
4. 记构建与运行方式：怎么装、怎么跑、怎么测
5. 标出已有文档与明显缺口

**输出**：`.work/01-map/codemap.md` —— 文件树、入口点、依赖清单（含版本与来源文件）、构建运行方式、已有文档清单。**只记「是什么」，不写「为什么」。**

**为什么不能写判断**：后面三个阶段的结论都要回到这份地图上核对。地图里混进一句「这个模块是核心」，下游会围着这句猜测写一整章。

---

## Phase 2：架构认知（Atlas Vaughn）

**输入**：`.work/01-map/codemap.md`（整篇读完）。

**内部运作**：

1. **分层画像**：按职责切成几层（接入 / 业务 / 领域 / 基础设施之类），给每层一句话职责，并指到真实目录
2. **业务模块识别**：把项目切成用户能理解的业务/功能模块——不是文件目录的照抄，而是「这个系统能做什么事」的切分。每个模块给：一句话职责、所在层、依赖谁、被谁依赖
3. **全局运行流程**：挑一到三条主链路，从入口一路走到落点，每跳标 `文件:行号`

**输出**：三份文件
- `02-arch/layers.md`：分层画像 + 每层职责与目录
- `02-arch/modules.md`：模块清单表（模块 / 一句话职责 / 所在层 / 依赖 / 被依赖）
- `02-arch/flows.md`：一至三条主链路的逐步推演

**为什么先分层再切模块**：分层回答「代码怎么摆」，模块回答「用户能用它做什么」。两件事混在一起写，读者分不清哪是结构、哪是功能。

---

## Phase 3：模块深挖（Atlas Vaughn 主笔，Evan Trace 补代码路径）

**输入**：Phase 2 的三份文件 + 代码地图。

**内部运作**：对 Phase 2 列出的**每一个**模块，写清四件事：

1. 这个模块在整体里的位置（属于哪层、被谁调用、调用谁）
2. **输入**：它接收什么（请求参数 / 事件 / 数据集 / 上游产出），从哪来
3. **内部运作**：进来之后按什么顺序处理——关键函数与数据结构，从哪到哪
4. **输出**：产出什么，给谁用

再加一句边界：这个模块**不负责**什么。缺了这句，读者会把相邻模块的职责算到它头上。

**输出**：`.work/03-deepdive/<模块名>.md`，一模块一份。

**为什么必须逐个模块过**：项目级流程只讲主干，跨模块交界处最容易「看起来讲完了」。逐模块写「输入-内部运作-输出」，交界处的空白会立刻暴露——上一个模块的输出没出现在下一个的输入里，就是漏了一环。

---

## Phase 4：写前冻结（Vera Cross）

**输入**：Phase 2 与 Phase 3 的全部产物。

**内部运作**：

1. 扫一遍全部模块文档，抽出**同一概念的不同叫法**，每个概念定一个正名，其余列进 `_Avoid_`
2. 找出**会被两篇都写的东西**（完整枚举、抽象基类、参数表、建表语句），各指定唯一 owner 文件
3. 定死附录编号风格（只用「附一 / 附二」）

**输出**：`freeze/glossary.md`、`freeze/ownership.md`，细则见 `references/glossary-and-ownership.md`。

**为什么必须在动笔前**：写完再统一术语，要全库搜一遍改几百处；而冻结只要半小时。写手分散在多个子 agent 里，彼此看不到对方用了什么词——只有冻结能拦住这件事。

---

## Phase 5：写作（Lena Quill + Cleo Spark，并行）

**输入**：Phase 2 / 3 的全部产物 + `freeze/glossary.md` 与 `ownership.md`（整篇读完）。

**内部运作**：

- **Lena Quill** 定目录骨架，写 `01-整体架构/`、`02-技术栈/`、每个主题的 `02-功能流程与架构.md`；把架构图与流程图的 SVG 源码落成 `assets/<与本章同名子目录>/` 里的文件，负责路径、`alt`、目录归属
- **Cleo Spark** 写 `00-项目综述/`、每个主题的 `00-来龙去脉.md` / `01-亮点难点.md` / `03-具体实现.md`、`04-面试与简历/`

两人写范围不重叠。每批开工前先读 `05-authoring/toc.md` 确认章节顺序，写承接时读上一步的 `00` 与收尾篇小结。用词只准用 `glossary.md` 的正名，禁止 `_Avoid_` 里的词；拿不准标 `待定` 回给主理人。

**输出**：全部章节正文 + `assets/` + `05-authoring/toc.md`。

**为什么要有 toc**：分批写作时，后一批的写手看不到前一批的思路。目录骨架是唯一能让两批保持同一套编号与承接关系的东西。

---

## Phase 6：交付闸门（主理人 + Vera Cross）

**输入**：全部章节 + 两条冻结文件。

**内部运作**：

1. 拍快照：复制整个教程目录到 `../<项目名>-拆解教程.bak-<时间戳>/`
2. 跑 `scripts/audit_teardown.py`，error 清零；warn 逐条判断是「可接受」还是「漏产」
3. 脚本查不出的交 Vera Cross：图里画的调用顺序对不对、简历条目有没有落点、数字口径有没有位移
4. 生成 `README.md` 导航表，链到每一个文件

**输出**：修正入稿的教程目录 + `README.md` + `06-review/checklist.md`。

**为什么闸门放在最后**：前面每一步都在放大内容，最后一处集中检查比每步零散检查便宜。**脚本有 error 就不许汇报**——这不是建议，是闸门的定义。

---

## 汇报（Phase 6 结束时给用户）

目录树 + 章节清单表（路径 / 标题 / 核心内容一句话）+ 配图清单 + **脚本结论一行（error/warn 数）** + 阅读路径建议 + 遗留风险（含有意舍弃的素材及理由）。
