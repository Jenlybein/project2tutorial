# 流水线与交接契约（pipeline）

本文件给出**每个 Phase 的输入、产出、验收标准与交接规则**；档位与 Phase 序列的唯一真相源是 `references/workflows.md`，两者分工不要混：先查 workflows 决定跑哪几段，再按本文件逐段派工。角色定义见 `SKILL.md` 的六角色表与 `references/roles/<id>.md`，单点直调路由见 `references/workflows.md`。

## 阶段产物文件约定：文件即消息总线

交付目录：`<项目名>-拆解教程/`（建在用户当前工作目录下）。
工作区：`<项目名>-拆解教程/.work/` —— 中间产物，**不交付、不进 README 导航、审计脚本会跳过**。

| 阶段 | 谁做 | 中间产出（`.work/`） | 交付产出（教程目录内） |
|------|------|---------------------|----------------------|
| 0.5 底座 | engineer | `00-base/baseline.md` | — |
| 1 分析 | architect / engineer / ui（按需） | `10-analysis/architect.md`、`10-analysis/engineer.md`、`10-analysis/ui.md` | — |
| 2 架构定稿 | architect | `20-arch/final-architecture.md`（含「口径冻结表」一节） | — |
| 2.5 横向清单 | auditor | `25-crosscut/lists.md`、`28-authoring/numbers.md`、`28-authoring/unique-ownership-candidates.md` | — |
| 2.8 冻结 | writer | `28-authoring/glossary.md`、`28-authoring/ownership.md` | — |
| 3 写作 | writer + creator（并行、写文件范围不重叠） | `30-authoring/toc.md`、`30-authoring/teaching.md` | `00-项目综述/`、`01-整体架构/`、`02-技术栈/`、各步四件套、`额外补充.md`、`assets/` |
| 4 复现总纲 | creator | `40-repro/repro-outline.md` | `03-实现开始/00-复现总指引/` |
| 5 三向检查 | writer / engineer / auditor（**只出清单不改正文**） | `50-review/writer.md`、`50-review/engineer.md`、`50-review/auditor.md` | — |
| 5.5 面试简历 | creator，然后 auditor 核 | `55-career/pitch.md`、`55-career/traceability.md` | `04-面试与简历/` |
| 6 汇编 | 主理人 | — | 修正入稿、`README.md`、最终审计 |

`.work/28-authoring/` 下的四份文件有两个来源，别记混：**`numbers.md` 与 `unique-ownership-candidates.md` 是 Phase 2.5 由 auditor 建档**；**`glossary.md` 与 `ownership.md` 是 Phase 2.8 由 writer 冻结**。口径冻结表（canon）不另起文件，它是 Phase 2 定稿里的一节。四个文件的字段与自检 12 条见 `references/canon-and-glossary.md`。

四条交接纪律：

1. **完整正文必须落成文件。** 子 agent 的回复只做交接（≤10 行：写了哪些文件、关键判断、未决项）。禁止靠「把长文回传给你」传递内容——摘要一旦进上下文，下一阶段就只能基于摘要工作。
2. **下一阶段的输入是文件路径 + 一句「整篇读完再开工」**，不是摘要、不是节选；**凡是列进 prompt 的文件都要整篇读完**。唯一例外是 Phase 3 后续批次按「派工输入三层」不把架构定稿全文列进输入，只列 `toc.md` 索引 + 本批相关小节，该节仍整篇读完——少带文件，不缩水读。
3. **同一阶段并行的成员，写文件范围必须互不重叠。** 重叠就改串行；没有别的办法。
4. **Phase 5 只出清单。** 三方向同时改同一批正文必然互相覆盖。清单完成后，主理人**在 Phase 5 末尾做一次串行合稿**，把修正写回正文形成定稿；Phase 5.5 只基于这份定稿写，Phase 6 不再重复合稿，只做汇编与闸门。改动量大时按章节分批派新的写作子 agent 落盘。

> 质控组与 `senior-engineer` 的分工：**工程师校验「能不能跑通」，查秋毫校验「漏没漏、对不对得上」**。前者看命令与版本，后者看忠实度与完整性，两者不互相替代。

## 标准工作流程（SOP）

### Phase 0：需求与素材确认（主理人亲自完成，不委派）
向用户确认五件事，缺一不可（没给全就问，不要替他决定）：
1. **项目来源**：本地路径 / 仓库 URL / 压缩包 / 上传文件
2. **目标读者**：新手入门 / 有基础的开发者 / 架构研究者（决定术语解释的深度）
3. **教程深度**：只要架构讲透，还是要求能跟着代码复现
4. **输出目录**：默认在用户当前工作目录下创建 `<项目名>-拆解教程/`
5. **素材范围**：源素材有多少篇、按什么方式组织（按迭代 / 按专题 / 按模块）。这份清单是 Phase 2.5 覆盖率对账的基准——**摸不清它，后面就无法判断「漏没漏」**。

确认后按 `references/workflows.md` 选档，并向用户通报本轮将执行的 Phase 序列。

### Phase 0.5：结构底座（串行，全员共享的事实底座）
将项目源码位置交给 `senior-engineer`，产出一份**不含任何判断**的客观清单：文件树、入口点、依赖图、构建运行清单、已有文档清单、复杂度初判。

**这一步的目的是消灭口径分歧。** 两到三个分析成员各自摸索同一份代码库，必然得出互相矛盾的结论；全员基于同一份底座开工，分歧的地基就没了。

**铁律：底座只记录「是什么」，禁止写「为什么」。** 不写职责判断、不写设计意图、不写选型理由——那些是 Phase 1/2 的活。混进判断的底座会污染下游所有分析。

产出后，把**底座完整原文**作为 Phase 1 所有成员的共同输入一起下发。

### Phase 1：多视角协同分析（并行）
在同一轮里同时启动分析组成员（并行、互不通信），各自只写自己的报告文件：
- `software-architect` → 架构视角分析报告（**必拉**）
- `senior-engineer` → 执行路径分析报告（**必拉**）
- `ui-designer` → 界面交互分析报告（**按需**：仅在项目有界面时拉——Web 前端、桌面端、移动端、管理后台、可视化页面。纯后端服务、CLI 工具、库/SDK、算法项目**跳过**，不要为凑人数硬拉）
  - 例外：无界面但结构复杂、教程预计配图较多时，可以只拉他做一件事——产出《配图视觉规范》（配色、节点样式、字号层级、图例画法），不做界面分析。这样多个成员分头画的图才能看起来是一套。

输入：**Phase 0.5 结构底座（完整原文）** + 项目源码位置 + 目标读者 + 教程深度。
输出：结构化分析报告，写入指定报告文件，并向主理人回传简短交接。
每份报告都必须包含技术栈结论：架构师给分层清单、工程师给精确版本及其来源文件、设计师给 UI 组件库与设计体系。
若跳过 `ui-designer`，架构师报告中需补一句「本项目无界面层」，避免后续章节凭空冒出界面内容。

### Phase 2：架构定稿（串行）
把 Phase 1 **已产出的分析报告**（必有的 2 份 + UI 按需的第 3 份）文件路径交给 `software-architect`，要求他**整篇读完再动笔**，产出：
- 《整体运行架构》：分层/分模块全景、启动到就绪的全过程、外部依赖
- 《各功能模块运行架构》：模块清单表 + 逐模块的功能、作用、运行流程、对外接口，复杂模块补技术实现方式（直接支撑 `01-整体架构/02-模块详解.md`）
- 《运行细节》：关键链路的逐步推演、状态流转、模块间契约、失败与边界处理
- 《技术栈全景》：分层清单、精确版本、各自用途、选型理由、官方文档入口（供 `02-技术栈/` 直接使用）
- **《口径冻结表（canon）》**：作为定稿的独立一节，冻结会演进的事实、被多章引用的结论、易被改写的定义；表结构与规则见 `references/canon-and-glossary.md`

### Phase 2.5：横向清单抽取（串行，动笔前必做）
把**口径来源**（A：Phase 2 定稿；C：用户已有架构说明 + 已有源码；D：源素材清单）交给 `source-auditor`（要求整篇读完），抽取六张表：数字清单、上限与配额清单、能力边界清单、量化结论清单、前后矛盾清单、待补缺口清单。

这一步为什么必须在写作前做：源素材常按**横向专题**组织（亮点、优化轮次、设计原则），而教程按**纵向步骤**切分。那些不属于任何单一步骤的数字、上限、边界、量化结论，在重组时最容易无处安放而丢失，事后很难发现。

清单产出后兵分两路：给 `content-creator` 作为 `额外补充.md` 的原料；给 `longform-writer` 作为写章节时的防漏锚点。**清单里每一项最终都要有落点，或明确标注为有意舍弃。**

本阶段同时产出两份「对账用」的文件，落在 `.work/28-authoring/`：

- `numbers.md`：数字账本，一个指标一行，列「值 / 口径（实测·自述·文档声明）/ 出处 / 引用章节」。Phase 5 拿它机械对账。
- `unique-ownership-candidates.md`：预判「同一个东西会被两篇都写」的位置（错误码全表、Provider 抽象基类、档位参数表、建表 DDL），供 Phase 2.8 定 owner。

### Phase 2.8：冻结词表与唯一归属（串行，动笔前必做）

把**口径来源**与 Phase 2.5 的 `numbers.md`、`unique-ownership-candidates.md` 交给 `longform-writer`（要求整篇读完）。口径来源随档位变化，别一律去翻 Phase 2 定稿：

| 档位 | 口径来源 |
|---|---|
| A-全量 | Phase 2 定稿里的「口径冻结表（canon）」一节 |
| **A-lite** | **`senior-engineer` 的 0.5/1/2 合稿里的 canon 一节**；不另找 `.work/20-arch/final-architecture.md` |
| C | 用户已提供的架构说明（缺 canon 时先用「前后矛盾清单」兜底） |
| D | Phase 2.5 的「前后矛盾清单」+ 源素材里的命名与定义 |

产出 `.work/28-authoring/` 下的两个文件：

- `glossary.md`：术语表。每个概念一个正名 + 一句话定义 + `_Avoid_` 避用词清单；附录编号风格在这一步统一（只用「附一 / 附二」，不许「二、三、八、8.1」混排）。
- `ownership.md`：唯一归属表。每段代码、每张表、每个口径指定一个 owner 文件；其余章节只能写「本步增量 + 指路 + 本步的坑」。

**为什么必须在 Phase 3 之前冻结**：四十多篇的教程，一致性靠「写的人记性好」不成立；不冻结，这些债到 Phase 5 只能用人眼全库扫一遍来还。完整事故复盘与字段细则见 `references/canon-and-glossary.md`。

派工时把这一句写进 prompt 作为硬约束：**「只准使用 `glossary.md` 里的正名，禁止 `_Avoid_` 列出的词；拿不准的标 `待定` 回给主理人，不要自己造。」**

### Phase 3：目录化、章节化与教学表达（角色随档位裁剪）

**角色随档位裁剪**（以 `references/workflows.md` 的「A 档规模分流」为准）：

| 档位 | 谁写 | 为什么 |
|---|---|---|
| A-全量 / C | `longform-writer` + `content-creator`，写范围不重叠 | 有源码或已有架构，既要结构成文也要教学表达 |
| **A-lite** | **仅 `longform-writer`**，一人写全套四件套 | 小项目章节少，双写手的交接成本超过收益；由 Phase 5 换人双查补偿 |
| D | 仅 `longform-writer` | 素材重组型无复现步骤，不拉 `content-creator`、不产实操三篇 `01-亮点难点.md` / `02-功能流程与架构.md` / `03-具体实现.md`；但每章仍由主笔写**独立** `00-来龙去脉.md`（讲清该章的来路与承接），不跑 Phase 4 |

A-lite 的 0.5 / 1 / 2 在 Phase 0 后合并为一次 `senior-engineer` 合稿（底座 + 执行路径 + 架构结论 + canon 口径冻结表一节），作为本阶段的**结构来源**。

把**结构来源**（A-全量：Phase 2 定稿；A-lite：0.5/1/2 合稿；C：用户已有架构说明；D：素材底座的主题聚类）、Phase 2.5 横向清单、**Phase 2.8 的 `glossary.md` 与 `ownership.md`** 的文件路径交给本档的写作成员，按 `references/output-spec.md` 的「四件套分工」与「叙述链三问」成稿。
- `content-creator`（**A-全量 / C 才拉**）→ 每个步骤**先写 `00-来龙去脉.md`**：承上、当前项目进展、为什么做这个功能、做完是什么样、四篇阅读地图、启下；再写 `01-亮点难点.md` 与 `03-具体实现.md`（含驱动提示词原文）。另产 `00-项目综述/` 各篇与跨章节的 `额外补充.md`；同时产出概念示意图与封面（概念图优先手写 SVG；封面与氛围图可用 AI 生图，必须标注「示意图」并记录提示词）
- `longform-writer` → 先定目录骨架与章节序列（顶层导读章 + 实现步骤序列），再撰写 `01-整体架构/`、`02-技术栈/` 各篇，以及每个步骤的 `02-功能流程与架构.md`（本步改了什么、一次调用怎么流转、契约与边界）；**并把报告里的 SVG 图源码落成文件放进 `assets/<与本章同名的子目录>/`**，正文用相对路径引用，`alt`、目录归属与路径层级由他负责。**A-lite 与 D 档下，他一人接手全部四篇**（`00` 仍独立成篇），写范围无需拆分。

**四篇各只回答一个问题**：`00` 讲「为什么走到这一步」、`01` 讲「难在哪、值在哪」、`02` 讲「做了什么、怎么流转」、`03` 讲「怎么动手、怎么算做成」。`01`/`02`/`03` 开头只用一句话回指 `00` 的结论，不重写背景；每篇结尾一句交接。每个知识点过「从哪来 / 为什么现在 / 到哪去」，语言尺度按 `references/output-spec.md` 的「给初级程序员看，但不哄人」。

**批次**：A-全量 / C 按 2–3 个章节或步骤一批；**A-lite 按 4–5 章一批，单写手 2–3 批**；D 按主题聚类一批。每批都是新的子 agent，批次之间串行。

**派工输入分三层，别每批把同一批定稿整篇重读一遍**（这是比派工次数更贵的 token 开销）：

| 层 | 内容 | 每批怎么带 |
|---|---|---|
| 常带（短且稳定） | `glossary.md`、`ownership.md`、`numbers.md`、`30-authoring/toc.md` | 每批完整给路径，要求读完 |
| 只读一次 | **本档结构来源**（架构定稿 / 合稿 / 已有架构说明 / 素材底座）与 Phase 2.5 横向清单 | **只在第一批整篇读**；后续批次**不把全文列进输入**，只列 `toc.md` 索引 + 与本批相关的那一节路径，该节仍要求整篇读完。少带文件，不缩水读 |
| 增量带 | 上一步 `00-来龙去脉.md` 与**收尾篇小结**（`03-具体实现.md`，若 `01`/`02`/`03` 已合篇则为合并后的那一篇） | 每批带上一步产物，保证承上启下不断链 |

**抽检只做一次**：第一批交稿后主理人派 `senior-engineer` 抽检代码示例能否跑通（早期纠偏），结论写入 `.work/30-authoring/`，不通过就随第二批修正；**后续批次不再逐批抽检**，命令、代码、版本、路径的可执行性整体交给 Phase 5 的「可执行」方向全量核对。写作期只跑 `scripts/audit_teardown.py` 能机械查的项。写范围互不重叠，细则见 `SKILL.md` 的「写范围与写冲突」。

### Phase 4：复现总指引（串行）
**A / C 才跑此阶段；D 档不跑**（素材重组型没有可复现的逐步操作）。把 Phase 3 已落盘的章节文件路径交给 `content-creator`（要求整篇读完），产出 `03-实现开始/00-复现总指引/`：`00-预先准备.md`（外部账号与能力）→ `01-路线图.md`（顺序 / 完成判据 / 全局验收）→ `02-环境准备.md` → `03-排错手册.md`。

**`00-预先准备.md` 必须先写。** 判据只有一条：凡是「要离开代码、去第三方控制台操作一次」的东西（模型 / 嵌入 / 重排 / 存储 / 支付 / 短信的账号、Key、权限、额度、地域）都归它；凡是「本地一条命令能装上」的（Docker、运行时、包管理器）一律归 `02-环境准备.md`。
三条硬规则：不写 `.env` 与变量赋值（那是环境准备章的事）、不写装环境步骤、原项目的专有模型名要标明可能不存在并给退路。
项目没有任何外部依赖时不要交空壳文件，在路线图开头写一句「无外部服务依赖，跳过预先准备」即可。细则见 `references/output-spec.md` 的「`00-预先准备.md` 该写什么」。
注意：逐步骤的来龙去脉已落在每步 `00-来龙去脉.md`，复现过程已落在每步 `03-具体实现.md`，本阶段只做**总纲**，不要重复写一遍逐步操作。
其中 `02-环境准备.md` 必须先给出**技术栈版本矩阵**（技术 / 精确版本 / 作用 / 安装命令 / 验证命令），读者照表即可装出一致的环境。

### Phase 5：改稿、技术校验与事实核验（并行，方向随档位裁剪）

**A-全量 / C 拉三方向；A-lite 拉 `senior-engineer` + `source-auditor` 两方向（换人双查，单写手不自查）；D 只拉主笔 + 审计两方向**（无环境准备与逐步命令，可省工程师的可执行校验）。把 Phase 3 +（跑了才有的）Phase 4 全部文稿、源素材清单、以及 `.work/28-authoring/` 下四份账本的文件路径交给本档检查成员（要求整篇读完）。三个方向互不替代：
- `longform-writer` → **表达**：术语统一、层级与编号一致、交叉引用正确、删冗余、补缺漏；同时核对图的位置（是否紧跟它解释的那段）与 `alt` 是否说清了图的作用 → 改稿清单
- `senior-engineer` → **可执行**：逐条核对命令、代码、版本号、路径是否可执行；并复核**图里画的技术结构对不对**——调用顺序、模块边界、箭头方向、状态分支是否与代码一致 → 技术校验清单
- `source-auditor` → **忠实与完整**：素材覆盖率对账（哪些吸收了、哪些漏了）+ 事实一致性核验（数字口径、前后矛盾、版本来源）+ 交付完整性核验（文件齐全、导航可达、链接不断、**图片引用可达、`alt` 齐全、AI 图有「示意图」标注、图文描述一致**） → 审计清单

> 本阶段三方**只写清单文件，不改正文**（并行改同一批文件必然互相覆盖）。三个方向的差别，用一句话记：主笔管「写得清不清楚」，工程师管「跑不跑得通」，查秋毫管「漏没漏、对不对得上」。**只做前两项，教程会「看起来很完整但少了东西」。**
>
> 每条清单必须带 `文件:行号` + 建议新文本；机械可查项先跑 `scripts/audit_teardown.py`，人只做判断项。**Phase 3 后续批次不再抽检，所以工程师在 Phase 5 必须逐条覆盖全部命令、代码、版本与路径**，不能只抽查。
>
> **A-lite 的 `source-auditor` 额外产出一份「素材落点索引」**（写在 `.work/50-review/`），标出每个数字、每处取舍支撑在**当前已落盘的章节文稿**哪一篇（`文件:行号`）。它在 Phase 5 清单阶段产出，早于合稿；主理人合稿时按索引核对修正有没有把落点改丢，Phase 5.5 再按同一份索引机械核对。
>
> **本档清单交齐后，主理人串行合一次稿**：把建议新文本写回对应章节文件，形成定稿，供 Phase 5.5 与 Phase 6 使用。这一步由主理人做，不是任意一个检查方向改正文。

### Phase 5.5：面试与简历拆解（串行，必须基于定稿）

> 前提：Phase 5 的本档清单已由主理人在该阶段末尾串行合稿，正文定稿已落盘。本阶段只基于定稿写，不基于草稿。定稿里没有的东西，这一章一个字都不许加。

把**定稿文件路径** + **Phase 2.5 横向清单**（重点：数字清单、量化结论清单）+ **规模数据**（A/C 有源码时来自 Phase 0.5 结构底座；D 用素材底座的篇数与主题数）交给 `content-creator`，产出 `04-面试与简历/` 四篇。

**这一步为什么值得单独一个 Phase：** 读者拆完一个项目，手里有一堆章节，缺的是**把这件事讲给别人听的能力**。而这套能力的原料，前面所有阶段其实已经生产完了——项目进展与各步起因在每步 `00-来龙去脉.md`，数字在 Phase 2.5，难点在每步 `01-亮点难点.md`，取舍在 `01-整体架构/04-设计决策.md` 与每步 `02-功能流程与架构.md` 的「关键设计决策与契约」，可验证的产物就是这套教程本身。不写这一章，这些原料只能躺在文件夹里。

**A-全量**（C 档默认不跑 5.5，只有用户明确要面试材料时才补）：产出后交 `source-auditor` 做一次**表述可溯源核验**：简历条目与面试答案里的每个技术断言、每个数字，是否都能在定稿里找到落点；有没有把「复现」写成「开发」、把推测写成事实、把 A 口径的数字说成 B 口径。**核验不通过的条目退回重写，不许带进 Phase 6。**

**A-lite**：`source-auditor` 已在 Phase 5 产出「素材落点索引」，主理人合稿时先确认落点没被改丢，5.5 再按索引机械核对；只有出现无落点、口径冲突或身份表述问题，才派 `source-auditor` 裁决并退回重写。

### Phase 6：汇编落盘（主理人亲自完成）
1. 处理 Phase 5.5 表述核验的修正项，以及 `source-auditor` 报出的「遗漏」项——补进正文，或在 README 里标注为有意舍弃并说明理由，不许静默丢弃。Phase 5 清单已在该阶段末尾合稿，此处**不再重复合稿**
2. 把剩余修正项写回磁盘上的章节文件，目录约定见 `references/output-spec.md`；`assets/` 先按章节建好子目录，图按章入场；落盘后跑一遍 `scripts/audit_teardown.py`（断链、配图路径、`alt`、Mermaid、字符画、SVG 合法性、导航覆盖），再**人工逐个点开图片引用确认路径可达**（相对层级最容易错，`../` 少一层就全图挂掉）
3. 生成 `README.md` 作为总索引与导航（导航表要链到每一个文件）
4. 按 `SKILL.md` 的「交付前必做」跑闸门并汇报；**脚本有 error 不许汇报**

## 汇报格式（Phase 6 结束时给用户）

见 `SKILL.md` 的「交付前必做」第 4 条：目录树 + 章节清单表 + 配图清单 + 脚本结论（error/warn 数）+ 阅读路径建议 + 遗留风险。**跑了 5.5 才加**面试简历章的三层讲法要点；未跑 5.5 的档位说明跳过理由。
