# 流水线与交接契约（pipeline）

主理人（Lead）按阶段派工。本文件给出每个阶段的输入、产出、验收标准与交接规则。

## 阶段产物文件约定：文件即消息总线

交付目录：`<项目名>-拆解教程/`（建在用户当前工作目录下）。
工作区：`<项目名>-拆解教程/.work/` —— 中间产物，**不交付、不进 README 导航、审计脚本会跳过**。

| 阶段 | 谁做 | 中间产出（`.work/`） | 交付产出（教程目录内） |
|------|------|---------------------|----------------------|
| 0.5 底座 | engineer | `00-base/baseline.md` | — |
| 1 分析 | architect / engineer / ui（按需） | `10-analysis/architect.md`、`10-analysis/engineer.md`、`10-analysis/ui.md` | — |
| 2 架构定稿 | architect | `20-arch/final-architecture.md` | — |
| 2.5 横向清单 | auditor | `25-crosscut/lists.md` | — |
| 3 写作 | writer + creator（并行、写文件范围不重叠） | `30-authoring/toc.md`、`30-authoring/teaching.md` | `00-项目综述/`、`01-整体架构/`、`02-技术栈/`、各步三件套、`额外补充.md`、`assets/` |
| 4 复现总纲 | creator | `40-repro/repro-outline.md` | `03-实现开始/00-复现总指引/` |
| 5 三向检查 | writer / engineer / auditor（**只出清单不改正文**） | `50-review/writer.md`、`50-review/engineer.md`、`50-review/auditor.md` | — |
| 5.5 面试简历 | creator，然后 auditor 核 | `55-career/pitch.md`、`55-career/traceability.md` | `04-面试与简历/` |
| 6 汇编 | 主理人 | — | 修正入稿、`README.md`、最终审计 |

四条交接纪律：

1. **完整正文必须落成文件。** 子 agent 的回复只做交接（≤10 行：写了哪些文件、关键判断、未决项）。禁止靠"把长文回传给你"来传递内容——摘要一旦进上下文，下一阶段就只能基于摘要工作。
2. **下一阶段的输入是文件路径 + 一句"整篇读完再开工"**，不是摘要、不是节选。
3. **同一阶段并行的成员，写文件范围必须互不重叠。** 重叠就改串行；没有别的办法。
4. **Phase 5 只出清单。** 三方向同时改同一批正文必然互相覆盖，正文修正统一在 Phase 6 由主理人串行合稿；改动量大时，再由主理人按章节分批派一个新的写作子 agent 去改。

## 标准工作流程（SOP）

### Phase 0：需求与素材确认（主理人亲自完成，不委派）
向用户确认五件事，缺一不可（没给全就问，不要替他决定）：
1. **项目来源**：本地路径 / 仓库 URL / 压缩包 / 上传文件
2. **目标读者**：新手入门 / 有基础的开发者 / 架构研究者（决定术语解释的深度）
3. **教程深度**：只要架构讲透，还是要求能跟着代码复现
4. **输出目录**：默认在用户当前工作目录下创建 `<项目名>-拆解教程/`
5. **素材范围**：源素材有多少篇、按什么方式组织（按迭代 / 按专题 / 按模块）。这份清单是 Phase 2.5 覆盖率对账的基准——**摸不清它，后面就无法判断"漏没漏"**。

确认后立即向用户通报本轮将执行的 Phase 序列。

### Phase 0.5：结构底座（串行，全员共享的事实底座）
将项目源码位置交给 `senior-engineer`，产出一份**不含任何判断**的客观清单：文件树、入口点、依赖图、构建运行清单、已有文档清单、复杂度初判。

**这一步的目的是消灭口径分歧。** 如果三个分析成员各自摸索同一份代码库，会得出互相矛盾的结论——真实案例：同一项目并行分析后交叉核对，撞出 7 处口径分歧，只能逐条回原文核实。让所有人基于同一份底座开工，分歧的地基就没了。

**铁律：底座只记录"是什么"，禁止写"为什么"。** 不写职责判断、不写设计意图、不写选型理由——那些是 Phase 1/2 的活。混进判断的底座会污染下游所有分析。

产出后，把**底座完整原文**作为 Phase 1 所有成员的共同输入一起下发。

### Phase 1：多视角协同分析（并行）
在同一轮里同时启动分析组成员（并行、互不通信），各自只写自己的报告文件：
- `software-architect` → 架构视角分析报告（**必拉**）
- `senior-engineer` → 执行路径分析报告（**必拉**）
- `ui-designer` → 界面交互分析报告（**按需**：仅在项目有界面时拉——Web 前端、桌面端、移动端、管理后台、可视化页面。纯后端服务、CLI 工具、库/SDK、算法项目**跳过**，不要为凑人数硬拉）
  - 例外：无界面但结构复杂、教程预计配图较多时，可以只拉他做一件事——产出《配图视觉规范》（配色、节点样式、字号层级、图例画法），不做界面分析。这样多个成员分头画的图才能看起来是一套。

输入：**Phase 0.5 结构底座（完整原文）** + 项目源码位置 + 目标读者 + 教程深度。
输出：结构化分析报告，写入指定报告文件，并向主理人回传简短交接。
每份报告都必须包含技术栈结论：架构师给分层清单、工程师给精确版本及其来源文件、设计师给 UI 组件库与设计体系。
若跳过 `ui-designer`，架构师报告中需补一句"本项目无界面层"，避免后续章节凭空冒出界面内容。

### Phase 2：架构定稿（串行）
把 Phase 1 三份报告的文件路径交给 `software-architect`，要求他**整篇读完再动笔**，产出：
- 《整体运行架构》：分层/分模块全景、启动到就绪的全过程、外部依赖
- 《各功能模块运行架构》：模块清单表 + 逐模块的功能、作用、运行流程、对外接口，复杂模块补技术实现方式（直接支撑 `01-整体架构/02-模块详解.md`）
- 《运行细节》：关键链路的逐步推演、状态流转、模块间契约、失败与边界处理
- 《技术栈全景》：分层清单、精确版本、各自用途、选型理由、官方文档入口（供 `02-技术栈/` 直接使用）

### Phase 2.5：横向清单抽取（串行，动笔前必做）
把 Phase 2 架构定稿与**全部源素材清单**的文件路径交给 `source-auditor`（要求整篇读完），抽取六张表：数字清单、上限与配额清单、能力边界清单、量化结论清单、前后矛盾清单、待补缺口清单。

这一步为什么必须在写作前做：源素材常按**横向专题**组织（亮点、优化轮次、设计原则），而教程按**纵向步骤**切分。那些不属于任何单一步骤的数字、上限、边界、量化结论，在重组时最容易无处安放而丢失，事后很难发现。

清单产出后兵分两路：给 `content-creator` 作为 `额外补充.md` 的原料；给 `longform-writer` 作为写章节时的防漏锚点。**清单里每一项最终都要有落点，或明确标注为有意舍弃。**

本阶段同时产出两份"对账用"的文件，落在 `.work/28-authoring/`：

- `numbers.md`（`source-auditor` 写）：数字账本，一个指标一行，列「值 / 口径（实测·自述·文档声明）/ 出处 / 引用章节」。Phase 5 拿它机械对账。
- `unique-ownership-candidates.md`（`source-auditor` 写）：预判「同一个东西会被两篇都写」的位置（错误码全表、Provider 抽象基类、档位参数表、建表 DDL），供 Phase 2.8 定 owner。

### Phase 2.8：冻结词表与唯一归属（串行，动笔前必做）

把 Phase 2 定稿里的**口径冻结表（canon）**与 Phase 2.5 的两份候选清单交给 `longform-writer`（要求整篇读完），产出 `.work/28-authoring/` 下的两个文件：

- `glossary.md`：术语表。每个概念一个正名 + 一句话定义 + `_Avoid_` 避用词清单；附录编号风格在这一步统一（只用「附一 / 附二」，不许「二、三、八、8.1」混排）。
- `ownership.md`：唯一归属表。每段代码、每张表、每个口径指定一个 owner 文件；其余章节只能写「本步增量 + 指路 + 本步的坑」。

**为什么必须在 Phase 3 之前冻结**：四十多篇的教程，一致性靠"写的人记性好"是不成立的。不冻结就会出现真实发生过的事故——同一个概念在全书三四种叫法（`chunk`/`证据`/`文档片段`）、同一份错误码枚举在两个文件里各贴一遍、同一个指标两个数字并存；而这些债到 Phase 5 只能用"人眼全库扫一遍"来还。

派工时把这一句写进 prompt 作为硬约束：**"只准使用 `glossary.md` 里的正名，禁止 `_Avoid_` 列出的词；拿不准的标 `待定` 回给主理人，不要自己造。"**

细则（表结构、替换脚本要求、自检 12 条、口径演进怎么标注）见 `references/canon-and-glossary.md`。

### Phase 3：目录化、章节化与教学表达（并行）
把 Phase 2 架构定稿与 Phase 2.5 横向清单的文件路径分别交给两名写作组成员（要求整篇读完），按 `references/output-spec.md` 的目录形态成稿：
- `longform-writer` → 先定目录骨架与章节序列（顶层导读章 + 实现步骤序列），再撰写 `01-整体架构/`、`02-技术栈/` 各篇，以及每个步骤的 `02-功能与架构.md`；**并把报告里的 SVG 图源码落成文件放进 `assets/<与本章同名的子目录>/`**，正文用相对路径引用，`alt`、目录归属与路径层级由他负责
- `content-creator` → 产出教学表达与实操内容：`00-项目综述/` 各篇、每个步骤的 `01-亮点难点.md` 与 `03-具体实现.md`（含驱动提示词原文）、以及跨章节的 `额外补充.md`；同时产出概念示意图与封面（概念图优先手写 SVG；封面与氛围图可用 AI 生图，必须标注"示意图"并记录提示词）

### Phase 4：复现总指引（串行）
把 Phase 3 已落盘的章节文件路径交给 `content-creator`（要求整篇读完），产出 `03-实现开始/00-复现总指引/`：`01-路线图.md`（顺序 / 完成判据 / 全局验收）→ `02-环境准备.md` → `03-排错手册.md`。
注意：逐步骤的复现过程已经落在每步的 `03-具体实现.md` 里，本阶段只做**总纲**，不要重复写一遍逐步操作。
其中 `02-环境准备.md` 必须先给出**技术栈版本矩阵**（技术 / 精确版本 / 作用 / 安装命令 / 验证命令），读者照表即可装出一致的环境。

### Phase 5：改稿、技术校验与事实核验（并行）
把 Phase 3 + Phase 4 全部文稿与源素材清单的文件路径交给三名成员（要求整篇读完），三个检查方向互不替代：
- `longform-writer` → **表达**：术语统一、层级与编号一致、交叉引用正确、删冗余、补缺漏；同时核对图的位置（是否紧跟它解释的那段）与 `alt` 是否说清了图的作用 → 改稿清单 + 定稿章节
- `senior-engineer` → **可执行**：逐条核对命令、代码、版本号、路径是否可执行；并复核**图里画的技术结构对不对**——调用顺序、模块边界、箭头方向、状态分支是否与代码一致 → 技术校验清单
- `source-auditor` → **忠实与完整**：素材覆盖率对账（哪些吸收了、哪些漏了）+ 事实一致性核验（数字口径、前后矛盾、版本来源）+ 交付完整性核验（文件齐全、导航可达、链接不断、**图片引用可达、`alt` 齐全、AI 图有"示意图"标注、图文描述一致**） → 审计清单

> 本阶段三方**只写清单文件，不改正文**（并行改同一批文件必然互相覆盖）。如下：
>
> 三个方向的差别，用一句话记：主笔管"写得清不清楚"，工程师管"跑不跑得通"，查秋毫管"漏没漏、对不对得上"。**只做前两项，教程会"看起来很完整但少了东西"。**

### Phase 5.5：面试与简历拆解（串行，必须基于定稿）

> 前提：先按 Phase 5 三份清单合并出**定稿**，本阶段只基于定稿写，不基于草稿。定稿里没有的东西，这一章一个字都不许加。

把**定稿文件路径** + **Phase 2.5 横向清单**（重点：数字清单、量化结论清单）+ **Phase 0.5 结构底座**（规模数据：文件数、目录深度、语言数、外部依赖数）交给 `content-creator`，产出 `04-面试与简历/` 四篇。

**这一步为什么值得单独一个 Phase：** 读者拆完一个项目，手里有一堆章节，缺的是**把这件事讲给别人听的能力**。而这套能力的原料，前面所有阶段其实已经生产完了——数字在 Phase 2.5，难点在每步 `01-亮点难点`，取舍在 `02-功能与架构`，可验证的产物就是这套教程本身。不写这一章，这些原料只能躺在文件夹里。

产出后交 `source-auditor` 做一次**表述可溯源核验**：简历条目与面试答案里的每个技术断言、每个数字，是否都能在定稿里找到落点；有没有把"复现"写成"开发"、把推测写成事实、把 A 口径的数字说成 B 口径。**核验不通过的条目退回重写，不许带进 Phase 6。**

### Phase 6：汇编落盘（主理人亲自完成）
1. 合并 Phase 5 三份清单与 Phase 5.5 表述核验的修正项到定稿；`source-auditor` 报出的「遗漏」项必须逐条处理——补进正文，或在 README 里标注为有意舍弃并说明理由，不许静默丢弃
2. 把修正项写回磁盘上的章节文件，目录约定见 `references/output-spec.md`；`assets/` 先按章节建好子目录，图按章入场；落盘后跑一遍 `scripts/audit_teardown.py`（断链、配图路径、`alt`、Mermaid、字符画、SVG 合法性、导航覆盖），再**人工逐个点开图片引用确认路径可达**（相对层级最容易错，`../` 少一层就全图挂掉）
3. 生成 `README.md` 作为总索引与导航（导航表要链到每一个文件）
4. 向用户汇报：章节清单、素材覆盖率、字数规模、阅读路径建议、遗留风险


## 汇报格式（Phase 6 结束时给用户）

目录树 + 章节清单表（路径 / 标题 / 核心内容一句话）+ 面试简历章的三层讲法要点 + 配图清单（哪类图几张、有几张 AI 示意图）+ 阅读路径建议 + 遗留风险。
