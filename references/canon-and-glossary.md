# 口径冻结 · 术语 · 唯一归属 · 数字账本

这四个文件（都在 `.work/28-authoring/`）是 **Phase 2.8 的产出**，也是 Phase 3 写作、Phase 5 检查、Phase 6 汇编的共同依据。

它们存在的理由只有一条：**一套 40+ 篇的教程，一致性不可能靠"写的人记性好"，只能靠"写之前就把词和账定死"。**

> 真实事故（本项目实测）：跳过这一环，交付前要还的债是——`chunk` / `证据` / `精排` / `业务方` / `用户反馈` 在全库各写各的、同一份错误码枚举在 2 个文件里各贴一遍、22 与 26 两个数字同时存在、4 篇超过 900 行、3 处 Mermaid 违反硬底线。这些没有一处是"文笔问题"，全是"没人先定"。

## 一、canon.md —— 口径冻结表

**谁写**：`software-architect`（在 Phase 2 定稿里，作为独立一节）
**解决什么**：同一件事在不同章节被写成不同说法。

### 只冻结三类东西

1. **会演进的事实**：错误码编号、密钥存储方式、组件/概念的命名、接口路径与边界。
2. **被多章引用的结论**：分层数量、Provider 类别数、链路阶段顺序、版本语义。
3. **一句话能说清、但极容易被改写的定义**：例如"中台不生成答案"。

**不要冻结**：实现细节、代码片段、图表（那些属于 `ownership.md` 和正文）。

### 表结构

| 事实 | 当前口径（唯一正确写法） | 历史口径（不许再出现，除标注演进处） | 引用章节 |
|---|---|---|---|
| 检索接口 | `POST /api/v1/rag/retrieve`，不返回 `context_text` | `/chat`（第一版设计，已否） | 00/01/03/11 |
| 错误码总数 | 26 个（含 `SUCCESS = 0`） | 22 个（早期枚举不全时的数） | 02/07 |
| Key 存储 | 本期**明文** `api_keys.key_value`；生产改「哈希 + 密文」 | 只存 SHA-256 哈希 | 01/05/11 |
| 鉴权函数 | `get_current_key` → `KeyContext` | `get_current_tenant` → `TenantContext` | 01/05/11 |
| 应用身份 | API Key 即应用身份，**没有 `app_id`** | `app_id` + Key 两套身份 | 01/05/11 |

### 四条规则

1. **下游只能引用，不能改写**。想在章节里换个说法，回 canon 改，改完在「引用章节」列补一行。
2. **历史口径列不是垃圾桶**。它记录"曾经这么写过"，用来识别残留；正文只在**讲解演进**时允许出现，且必须带 `📌 版本说明` 块。
3. **一行一个事实**。把"Key 存储 + 配额两级"塞一行，等于没冻结。
4. **canon 与 `output-spec.md` 的底线冲突时，底线优先**。

## 二、glossary.md —— 术语表

**谁写**：`longform-writer`（Phase 2.8，串行，在动笔之前）
**解决什么**：同一个概念在全书有多个名字；或者一个人造了新词。

### 格式（照抄，不要发明新格式）

```markdown
## <分组名>

**<正名>**：
<一句话定义，说清"它是什么"，不写"它很重要">。
_Avoid_: <避用词1>, <避用词2>, <英文或旧称>

**<正名>**：
...
```

分组建议按书的结构走（边界 / 身份与权限 / 知识与文档 / 检索管道 / 架构分层 / 延伸能力 / 接入面）。

### 三条硬规则

1. **一个概念只有一个正名**。同义表达进 `_Avoid_`，不许"两种都能用"。
2. **代码标识符不进 `_Avoid_`**。`chunk_id`、`chunks` 表、`CHUNK_SIZE`、`retrieve`、`RerankProvider` 是代码，一律不动；只有**中文散文里**的 `chunk` 才该写成「切片」。
3. **首现要给定义**。每章第一次出现术语时补一句"它是什么"，之后直接用，不再解释。

### 替换必须用脚本，且必须复查

- 用 Python 写替换脚本（放 `scripts/` 下），**不要用 PowerShell 改中文正文**。真实事故：PowerShell 把单元素数组摊平，导致一个子 agent 把全文 91 个左括号替换成数字 2，整篇重建才救回来。
- 替换规则要**按搭配写**，不要整词替换：`chunk 策略` → `切片策略`、`每个 chunk` → `每个切片`，而不是 `chunk` → `切片`（后者会打断 `chunk_id`）。
- 替换后必须做三件事：① 跑 `audit_teardown.py`；② 抽读 5 处上下文；③ 搜「中文 + 空格 + 中文」的残留（机械替换最典型的伤口是「一个　切片　到底」）。

## 三、ownership.md —— 唯一归属登记

**谁写**：`longform-writer`（Phase 2.8）
**解决什么**：同一段代码、同一张表、同一个结论在两个文件里各讲一遍，改一处漏一处。

### 表结构

| 被归属物 | 唯一归属文件 | 其他章节怎么处理 |
|---|---|---|
| `ErrorCode` 完整枚举 | `02-工程可维护性/03-具体实现.md` | 其余章只写"错误码见该篇步骤 1"，不重贴 |
| `DocumentParser` 抽象基类 | `03-文档处理链路/02-功能与架构.md` | `03-具体实现` 只写实现要点 + 指路 |
| 三档档位预设表 | `08-性能优化/02-功能与架构.md` | 05 章写"本期档位见第 8 步"，不复制表格 |
| `api_keys` 表结构 | `05-多租户体系/03-具体实现.md` | 11 章只写"本章消费该表，结构见 05" |

### 判定规则

- **一个事实/一个代码块/一张表，只能有一个 owner**。
- owner 的选择标准：**读者最可能在哪一篇停下来研究它**，就放哪一篇。
- 非 owner 章节写三件事：**这个能力在本步的增量** + **一句指路** + **本步特有的坑**。
- 跨篇复用同一张图可以（图不占正文语义），但**代码和表格不行**。

### 机械检查

`audit_teardown.py` 会对代码块与表格做指纹（首行 + 归一化后的长度），跨文件命中即报 `duplicate-block` warn。命中后两种处理：**指定 owner 并改写另一方**，或**确认是"演进对比"**（那就在两边都标注出处差异）。

## 四、numbers.md —— 数字账本

**谁写**：`source-auditor`（Phase 2.5 建档，Phase 5 对账）
**解决什么**：同一个指标在不同章节有不同数值，或者一个数字没有口径。

### 表结构

| 指标 | 值 | 口径 | 出处 | 引用章节 |
|---|---|---|---|---|
| Context Precision（baseline） | 0.909 | RAGAS 实测，Golden Set v1 | `优化十五` 评测报告 | 04/08/07 |
| 检索召回率提升 | 58% → 85% | 原项目自述（非 RAGAS，口径不明） | 素材复述 | 03 |
| 错误码总数 | 26 | 枚举逐条计数（含 `SUCCESS = 0`） | `02-工程可维护性/03` | 02/07 |

**口径只允许三种值**：`实测` / `自述` / `文档声明`。写不出是哪种，就标 `待核`，不许含糊。

### 三条规则

1. **一个指标只允许一个值**。要写区间或不同测试集，就拆成两行。
2. **正文引用数字时必须能对到账本**。对不上就是 Phase 5 的 error。
3. **简历与面试章的数字只能来自账本**，且必须带口径（"这是我们自述的综合口径，不是 RAGAS"比一个漂亮数字更有说服力）。

## 五、口径演进怎么标注

原素材在不同阶段换过说法时，**不要悄悄统一**——那会让读者对照原文时以为书错了。统一用这个块：

```markdown
> 📌 **版本说明**：<主题> 在 <哪一阶段> 是 <原口径>，从 <哪一阶段> 起改为 <现口径>。
> 本文以现口径为准；出现原口径的地方是在讲演进，不是笔误。
> 影响章节：<列出章节>
```

判断标准：**读者会不会拿它去对照原文档？** 会，就必须标。

## 六、结构自检 12 条（Phase 3 每批交稿前、Phase 6 汇编前各跑一遍）

1. 每篇恰好一个 H1，且在第一段。
2. 标题层级不跳级（`#` 不直接到 `###`）。
3. 没有「`###` 下挂 `## 一、`」这种倒置（附录条目必须是 `### 附一 · …`）。
4. 附录编号连续且只有一种风格（`附一 / 附二 / 附三`），不出现「二、三、八、8.1」混排。
5. 三件套导航里**不链接自己**（写「本篇（你在这里）」）。
6. 全角括号成对；`（）` 与 `()` 不混用。
7. 中文散文里不出现 `chunk` / `证据` / `精排` / `业务方` / `用户反馈`（代码标识符除外）。
8. 中文与中文之间没有多余空格（机械替换的后遗症）。
9. 代码块/表格的 owner 唯一，非 owner 章节用指路句。
10. 无 Mermaid、无字符画、无内联 SVG 源码（图一律 `.svg` 文件 + 相对路径）。
11. 单篇 ≤ 600 行；600–900 行必须有「本章怎么读」导航表；> 900 行必须拆文件。
12. 相对链接可达；跨目录用 `../目录/文件名`，同目录直接写文件名。
