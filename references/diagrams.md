# 配图规范（图是辅助，不是装饰）

本文件定死三件事：**哪些图值得画、能用什么形态画、怎么写才不出错**。全流程硬性前提：所有图都是**独立文件**，正文只写相对路径引用；**禁用 Mermaid**、**禁用字符画**、**禁止用 AI 生图代替结构图**。

**先立判断标准，否则会画出一堆废图。** 一张图值得画，唯一理由是它承载了**文字难以线性表达的关系**——空间层级、多方时序、多分支状态、数据流向。把「先装 A 再装 B」画成流程图属于浪费；把「请求从网关进、过三跳、落到哪张表」画成时序图，一张能替三段文字。

**不设每篇的图片数量配额。** 设配额只会逼出凑数的图——「适当」这个词要落实成判断标准，而不是平均数。

## 图型选择：只有三种合法形态

| 要表达的东西 | 用什么 | 为什么 |
|---|---|---|
| 分层架构、模块依赖、数据流向、调用链 | **手写 SVG** | 坐标完全可控，版式与配色能和全书统一 |
| 调用时序、多方交互、请求生命周期 | **手写 SVG** | 泳道式布局算好坐标就不会错位，见下方画法 |
| 状态机、生命周期、分支收敛 | **手写 SVG** | 同上 |
| 数据模型、表关系 | **手写 SVG** | 同上 |
| 抽象概念、教学比喻、章节封面 | **AI 生图** | 这类本来就不需要精确 |
| 真实界面 | **截图**（项目能跑起来时） | 截图的可信度高于任何示意图 |

> **三条硬禁令，全流程无例外：**
> 1. **禁止用 Mermaid**（包括 `graph` / `flowchart` / `sequenceDiagram` / `stateDiagram` / `erDiagram` 等任何图形）——本工坊的图一律手写 SVG。
> 2. **禁止用文字、字符、ASCII 或文本代码块"画"图**——`├──`、`┌─┐`、`-->`、`| a | b |` 拼出来的结构图、流程图、树形图，**不得出现在任何交付物里**（正文、分析报告、README 都算）。推理时脑中怎么想都行，但**输出里只允许出现真正的图形文件**。
> 3. **禁止用 AI 生图绘制架构图、流程图、时序图、ER 图。** 生成模型不理解这个项目的代码，它画出来的框和线是"看起来像那么回事"但内容随机——读者会把它当成真实结构记住，**这比不配图更害人**。

> 目录树要表达"项目怎么分层"时，如果它只是**文件清单**（`├── src/` 这种），用纯文本目录树是可以的——那是目录，不是图。它一旦被用来表达**模块关系和依赖方向**，就必须换成 SVG。

## 四类结构图的 SVG 画法（原来交给 Mermaid 的活，现在这么干）

手写 SVG 会翻车，几乎全部翻在"边画边猜坐标"。统一做法：**先把坐标算成数字，再落笔**。下面四种是最常画的，各有固定套路。

**通用前置：先算文字宽度，再定框**
- 中文字符宽 ≈ 字号 × 1.0，英文字母 ≈ 字号 × 0.55，数字/符号 ≈ 字号 × 0.6
- 框宽 ≥ 文字实宽 + 左右内边距 24px；框高 ≥ 字号 × 2.6
- 一行放不下就**主动换行成两个 `<text>`**，不要靠缩小字号硬塞

**① 分层图 / 模块图 —— 网格法**
- 先定常量：层高 80px、层间距 64px、模块宽 = (画布宽 − 2×边距 − (列数−1)×gap) / 列数
- 第 r 层、第 c 列的模块坐标 = `x = 边距 + c × (宽 + gap)`，`y = 顶部 + r × (层高 + 层间距)`——写成算式一次算完，别逐个目测
- 层与层之间**只画垂直箭头**；层内并列的模块不画箭头（并列即"同层"，画了就变成依赖了）
- 给每层左侧加一个浅色标签带（层名 + 层级色块），读者一眼知道这是第几层

**② 时序图 —— 泳道法**
- 先定参与方数量 n，把所有泳道 x 坐标先算成一个数组：`x_i = 左边距 + i × (画布宽 − 左右边距) / (n − 1)`
- 顶部画参与方方块（宽 ≥ 参与方名称宽 + 32），下方从每个方块中心垂下**虚线生命线**
- 消息 y 坐标 = `顶部 + 序号 × 行高`（行高 40px 起），**序号从 1 开始连续编**，不允许两条消息共用一行
- 箭头一律水平（调用向右、返回向左用虚线 + 空心箭头），箭头端点必须正好落在生命线上
- 需要表示"这段在等"时，在生命线上叠一个小矩形（宽 8px）覆盖该时间区间
- 每加一条消息就重排 y 坐标，别在空隙里硬塞

**③ 状态机 / 生命周期 —— 布点 + 贝塞尔**
- 节点统一半径（或统一宽高），中心点先按环形或网格排好，写下每个节点的 `cx/cy`
- 边用 `<path>` 二次贝塞尔（`Q`）：控制点沿**垂直于连线方向**偏移 20-40px，让双向边自动错开不重叠
- 自环用小弧（`A` 弧线）从节点右上出、左上回，别画成一个整圆盖住节点
- 分支收敛的地方，箭头**必须落到节点边框上**而不是节点中心（用边框交点算终点）
- 标注文字放在弧线外侧、离节点 ≥ 8px

**④ ER 图 / 数据模型 —— 正交折线**
- 实体用矩形按网格排，每张表一个框；框内第一行是表名（加底色），下面按行列字段名 + 类型
- 关系线用**正交折线**（先横后竖再横，`<path d="M x1 y1 H xm V y2 H x2">`），不用斜线，斜线在密集图里会糊成一团
- 基数标注（1 / N）写在**靠近对应实体那一端**，不要写在线的中间
- 关系线穿过别的实体时，绕开而不是压在上面

> 这四种画法的共同点：**所有坐标都是算出来的，不是画出来的。**先在手稿里把网格、泳道、节点坐标列成数字，再生成 SVG 字符串，出错率会低一个数量级。

## 手写 SVG 的硬要求

- **一律存成 `.svg` 文件**，落到 `assets/<与本章同名的子目录>/`，正文用相对路径引用；**禁止把 SVG 源码贴在正文代码块里当图**——那样读者看到的是代码，不是图
- 必须带 `viewBox`，宽度自适应，不写死 `width` / `height` 像素值
- **文字必须在框内**：先按上面的宽度算式估字数再定框宽，宁可加大框，也不能让文字压线或溢出（这是手写 SVG 最常见的翻车点）
- **配色随主题**：浅色主题浅底深字、深色主题深底浅字；不写死某一套主题的颜色
- 字体只用系统字体栈（`-apple-system, "Segoe UI", "Microsoft YaHei", sans-serif`），不引用外部字体文件
- 同类元素（节点、箭头、边框）在同一张图里样式统一；同一个概念在全书的图里用同一种画法
- 箭头语义要分清：数据流、调用方向、依赖方向不能混用同一种箭头（实线箭头 = 调用，虚线箭头 = 返回/异步，无箭头连线 = 同层并列）
- 图内文字用正文语言，专有名词与正文完全一致
- 交图前**自己把 SVG 文件打开看一眼**：坐标算错、文字溢出、箭头没接上，肉眼一眼能看出来，别把渲染就崩的文件丢给读者

## AI 生图的边界

- 只用于概念示意、教学比喻、封面这类**不承担事实准确性**的场合
- **必须标注**「示意图，非真实界面 / 非真实数据」——AI 图很像真的，不标注会被读者误当成项目截图
- 把提示词记到该篇末尾的「配图说明」里，便于日后重绘
- **图里的文字不要交给模型生成**（十有八九是乱码或错字）；需要文字标注的，用 SVG 画或后期叠加

## 存放与引用

**`assets/` 按章节分子目录，子目录名与章节文件夹同名。** 这样图跟着章节走，找图不用在几十个文件的扁平列表里翻；同时文件名也不用再带章节前缀了——目录已经分好了。

```
<项目名>-拆解教程/
├── 01-整体架构/
│   └── 01-架构总览.md
├── 03-实现开始/
│   └── 04-混合检索/
│       └── 02-功能与架构.md
└── assets/
    ├── 01-整体架构/
    │   └── 分层结构.svg
    ├── 03-实现开始/
    │   └── 04-混合检索/
    │       └── 检索时序.svg
    └── 04-面试与简历/
        └── 项目价值示意.png
```

**路径层级：`../` 的个数 = 引用文件相对教程根目录的目录层数。** 这是唯一容易错的地方，记法就一句「**先数自己在第几层，再写几个 `../`**」：

| 引用文件所在位置 | 层数 | 引用写法 |
|---|---|---|
| `README.md`、`额外补充.md`（根目录） | 0 | `assets/01-整体架构/分层结构.svg` |
| `01-整体架构/01-架构总览.md` | 1 | `../assets/01-整体架构/分层结构.svg` |
| `03-实现开始/04-混合检索/02-功能与架构.md` | 2 | `../../assets/03-实现开始/04-混合检索/检索时序.svg` |
| `03-实现开始/00-复现总指引/02-环境准备.md` | 2 | `../../assets/03-实现开始/00-复现总指引/环境验证流程.svg` |

- 命名：只写**图名**（`分层结构.svg`、`检索时序.svg`），中文可读优先，不带章节号与序号
- `alt` 文本必填，写清"这张图说明了什么"，不是写"架构图"
- **所有图都是文件**（SVG / PNG / 截图），一律进 `assets/`，正文只写相对路径引用；正文里不许出现任何图源码
- 图必须落在**与它所属章节同名**的子目录里；放错目录按缺陷计（日后按章维护时找不到）

> 为什么值得多套一层目录：平铺时图多了没法按章清理，改一章要在一堆文件里认名字；分子目录后，删一章的图就是删一个文件夹。代价是路径深一层，用上面那张表挡住就够。

## 谁画什么（防"谁都以为别人画"）

| 图类 | 谁出图源码 |
|---|---|
| 架构图、分层图、模块关系图、数据流图 | `software-architect` |
| 时序图、调用链、状态机、ER 图 | `senior-engineer` |
| 界面结构、交互链路、视觉体系图 | `ui-designer` |
| 概念示意图、教学比喻、封面 | `content-creator` |
| 全书配图视觉规范（配色/节点样式/字号） | `ui-designer`，无界面项目中当预计图量较大时按需拉一次 |

各分析成员在**报告里直接给出成品 SVG 源码**（完整 `<svg>` 标签 + `viewBox`，可直接存成 `.svg` 文件），主笔成文时落成文件、嵌到对应位置，并负责 `alt`、路径与位置正确——**引用完整性只有一个负责人，就是主笔。**

**报告里也不许出现 Mermaid 或字符画。** 分析报告虽不是最终交付物，但它是主笔唯一的图来源；报告里写成 Mermaid 或 ASCII，主笔只能照着错下去。**从报告这一步就交 SVG 文件。**

## 图不能替代文字

**每张图的前后文必须能独立读懂。** 检验方法：把图删掉，这段还说得通吗？说不通，说明你把结论藏进图里了。原因很实在——**图现在是独立文件，路径一断就全白**，搜索、复制、听读也都读不到图。所以正文自己必须把话说完，图只负责让它更快被看懂。

**正文改了，对应的图必须一起改。** 图文不一致按缺陷计，交 `source-auditor` 记录。
