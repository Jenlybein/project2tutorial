# 输出规范（交付物形态）

这是交付物该长成的样子。目录层级、文件夹命名、三件套的拆分方式**都可以随项目调整**——唯一不变的是判断标准：**读者能不能顺着目录一路读下去、一路做出来**。任何妨碍这一点的固定格式都可以改。

落盘目录：`<用户当前工作目录>/<项目名>-拆解教程/`

## 交付形态：分层目录 + 每步三件套

教程不是一份平铺的文件清单，而是一棵**按阅读顺序生长的目录树**：顶层给全局视角，往下「一个实现步骤 = 一个子文件夹」，每个步骤文件夹里固定三件套。

> ⚠️ **下面这套结构来自一次真实拆解实践，是参考格式，不是硬性模板。**
> 目录层级、文件夹命名、三件套的拆分方式，**都应当随项目实际情况调整**：
> - 项目小、模块少 → 可以合并层级，甚至退化成扁平的多章文件
> - 项目有别的组织逻辑（按端分前后端、按环境分部署）→ 顶层划分可以整个换掉
> - 某一步内容很少 → 三件套合成一篇；某一步很重 → 再往下分层
>
> 唯一不变的是判断标准：**读者能不能顺着目录一路读下去、一路做出来**。任何妨碍这一点的固定格式都可以改。

## `01-整体架构/` 的两条硬要求

**`01-架构总览.md` 必须回答"这个项目总共分成哪些模块"。** 全景图之后要跟一张模块清单表（模块 / 一句话职责 / 处在第几层 / 依赖谁 / 被谁依赖），让读者深入之前先拿到一张地图索引。只画分层图、不给模块清单，等于没说清结构。

**`02-模块详解.md`** 是架构总览的展开篇，逐模块讲清三件事：

```
## 模块 N：<模块名>

### 功能（它做什么）
（承担的具体职责，落到真实文件或目录）

### 作用（为什么需要它）
（没有它会怎样；它在整体里解决什么问题；对应的设计意图）

### 运行流程
（输入 → 内部逐步处理 → 输出 → 与谁交互，用 SVG 图或编号步骤表达；用编号步骤就能讲清的，不要为了配图而配图）

### 技术实现方式（模块复杂时才写）
（它到底是怎么做到的：关键数据结构、算法或策略、用到的中间件、核心代码结构；
  用大白话讲，让读者不只知道"有这个能力"，还知道"这个能力怎么落地"）
```

> 「技术实现方式」只在该模块确实复杂时补入——简单模块写了是冗余，复杂模块不写则读者只知概念、不知落地。判断标准是：**读者看完能不能自己想出大致的实现思路**。

## 与实现步骤章节的分工（防重复）

`02-模块详解.md` 是**横向按模块**切，回答"它是什么、干什么、怎么跑"，读者不动手也能读懂全貌；`03-实现开始/NN-<步骤名>/02-功能与架构.md` 是**纵向按步骤**切，回答"这一步怎么把它做出来"。

同一个模块可能在多个步骤里被反复改造：**模块详解只讲最终形态，演进过程留给步骤章节**。两边都要讲运行流程时，模块详解讲稳态流转，步骤章节讲本次改动带来的流转变化。

## 参考骨架：每步三件套

```
01-亮点难点.md —— 先讲「为什么」，让读者在碰代码之前先站到设计者的位置
  ① 本步交付什么
  ② 为什么要做（一条痛点一段，配真实场景）
  ③ 亮点
  ④ 难点
  ⑤ 前置概念扫盲（本步才用到的新概念，用大白话讲）
  ⑥ 链路位置（这一步落在整体链路的哪一段）

02-功能与架构.md —— 讲「是什么、怎么流转」
  ① 整体架构（本步涉及的技术栈 + 结构图 / 管道图）
  ② 运行流程（一次调用的端到端流转，含异常与降级分支）
  ③ 关键设计决策与契约（逐条：决策内容 / 为什么 / 代价）
  ④ 边界（与什么解耦、本步不做什么）

03-具体实现.md —— 讲「怎么把它做出来」
  ① 环境 / 前置
  ② 实现步骤（逐步命令 + 代码 + 真实文件路径）
  ③ 每步验证点（看到什么才算通过）
  ④ 常见误区 / 排错
  ⑤ 小结 + 下一步
  ⑥ 驱动提示词原文（若原项目由提示词驱动，把可直接复用的提示词原文放在这里）
     附录编号只有一种风格：`### 附一 · …`、`### 附二 · …`；禁止「二、三、八、8.1」这类从原素材带过来的断档编号，
     也禁止把附件条目写成 `##`（那会和正文一级小节抢层级）
```

## 参考骨架：`04-面试与简历/`

**先定三条取材铁律。** 这一章最容易写成网上的面试八股——通用 STAR 模板、堆满"高并发 / 高可用"这类跟本项目无关的词。而它全部的价值，恰恰在于**从这份拆解里长出来**：

1. **禁止通用模板**：每个简历条目、每条面试答案的素材都必须来自定稿正文或源码。写进去的技术点、数字要能在正文里找到落点并带溯源。**正文里没有的，一个字都不许加。**
2. **禁止冒领作者身份**：这份作品的性质是**独立复现 + 架构拆解 + 技术写作**，不是"我开发了这个系统"。只能说自己真做过的事——照教程把系统搭起来、读懂并拆清了它的设计、把过程写成了 N 万字文档。把复现说成开发，面试官追问两轮就穿帮，而这类穿帮属于诚信问题，比技术答错严重得多。
3. **必须可核验**：拆解类作品的优势恰恰是**有公开产物**（教程目录 / 复现仓库 / 笔记）。能指向产物的就指向产物；核验不了的形容词（"精通""深刻理解"）一律删掉。

```
01-项目陈述.md —— 同一段经历的三层讲法
  ① 一句话版（20 秒，自我介绍里用）：是什么系统 + 解决什么问题 + 我做了什么
  ② 三分钟版（项目环节）：背景与目标 → 我实际做的事 → 只挑一个难点讲透 → 收获与产物在哪
  ③ 十五分钟版（深挖环节）：1-2 个模块的设计取舍，按「问题 → 方案 → 代价 → 我怎么验证的」展开
  ④ 钩子设计：主动留一个能引到你准备最充分处的钩子，并写明这个钩子后面要接住什么

02-简历写法.md —— 可以直接粘贴的文字
  ① 项目条目（3-5 条 bullet，每条：动作 + 技术 + 可验证的结果，末尾标素材出处）
  ② 技术关键词（只列真正动过手的，按熟悉度分档，不堆砌）
  ③ 规模数字（取自 Phase 2.5 与结构底座，每个数字标明口径：自述 / 实测 / 文档声明）
  ④ 按岗位的改写版本（后端 / 算法 / 工程效能 / 技术文档，各一版侧重）
  ⑤ 明确不写的词（本项目没做过的事，列成禁用表述清单）

03-面试问答拆解.md —— 会被问什么，考察点在哪儿
  | 问题 | 面试官真正在考察什么 | 答题骨架 | 素材出处（定稿哪一篇） | 不要说什么 |

04-追问与避坑.md —— 你的答案会在哪里被拆穿
  ① 高危追问清单：| 追问 | 为什么会问到这里 | 你能诚实答到的上限 | 该怎么答（含"这是我的推测"的说法） |
  ② 四个必须诚实的地方：设计意图（你不在场，只能推测）/ 线上故障（没有真实运维经历，别编故事）
     / 数字口径（自述还是实测）/ 团队角色（这是独立复现，不是团队协作）
  ③ 反向提问清单：问面试官的问题，能反过来体现你拆解时看出的深度
```

> 一条判断标准贯穿这四篇：**凡是写进去的，都要能在被追问三层时仍然答得出来。** 答不出来的技巧宁可不要——写进去等于给自己挖坑。

## 页型写作指令（每类文件写什么、明确不写什么）

光有骨架不够，还要说清**这一类文件不该写什么**——重复内容的根源从来不是没骨架，而是各篇都以为自己该讲。

| 页型 | 写作目标 | 明确不写 |
|------|---------|---------|
| 架构总览 | 给一张地图索引：分几层、有哪些模块 | 不展开实现细节 |
| 模块详解 | 讲清「是什么 / 干什么 / 怎么跑」 | 不写迭代历史（演进留给步骤章节） |
| 目录与验证 | 让人能对着目录验活 | 不重复讲模块职责 |
| 设计决策 | 讲决策的取舍与代价 | 不复述功能 |
| 亮点难点 | 建立「为什么」的动机 | 不提前倒代码 |
| 功能与架构 | 讲本次改动带来的流转变化 | 不重复模块详解的稳态流转 |
| 具体实现 | 手把手做出可验证的结果 | 不给没有验证点的命令 |
| 预先准备 | 只写**外部**要开通/申请的东西：账号、Key、地址、模型权限、额度、区域；每项都答「从哪步需要 / 要多久 / 花钱吗 / 能不能拖」 | 不写装环境与依赖工具（Docker / uv / pnpm / Node 归环境准备）；不写 `.env` 怎么填、不给变量赋值；不动项目文件 |
| 复现总指引 | 给全局顺序与完成判据 | 不重复逐步操作 |
| 排错手册 | 收跨步骤的通用故障 | 不写单步专属的坑（那些留在该步 `03-具体实现.md`） |
| 额外补充 | 收跨章节的高价值速查 | 不重复正文已有的成段讲解 |
| 项目陈述 | 同一段经历的可伸缩讲法（20 秒 / 3 分钟 / 15 分钟） | 不复述技术细节（细节是问答环节的事） |
| 简历写法 | 极限压缩、可直接粘贴的文字 | 不写正文里没有的技术点与数字 |
| 面试问答 | 问题 + 考察点 + 答题骨架 + 素材出处 | 不给背诵式标准答案（要留出个人化的余地） |
| 追问与避坑 | 哪里会被拆穿、怎么诚实应对 | 不教人编故事糊弄 |

## `00-复现总指引/00-预先准备.md` 该写什么

这一篇存在的唯一理由：**读者在敲第一条命令之前，会卡在「我还没有那把 Key」上**。教程里所有需要他离开代码、去第三方控制台操作一次的东西，都在这里一次说清。

### 判定规则：什么进得来，什么进不来

| 现象 | 判定 |
|---|---|
| 要去别人的控制台注册、实名、开通、建 Key、提额度、选地域 | ✅ 进「预先准备」 |
| 收费或有限额（按 token / 按调用 / 免费额度） | ✅ 进「预先准备」（必须写清花钱吗） |
| 账号里的模型名 / 端点地址可能和教程写的不一样 | ✅ 进「预先准备」（必须给确认方法与退路） |
| 本地一条命令就能装上（Docker、运行时、包管理器、数据库容器） | ❌ 归 `02-环境准备.md` |
| 参数怎么写进 `.env`、变量叫什么 | ❌ 归 `02-环境准备.md`（本篇只负责「拿到」，不负责「填进去」） |
| 报错怎么排查 | ❌ 归 `03-排错手册.md`（本篇只留「自检不通时看哪个错误码」） |

一句话：**本篇是「采购清单」，不是「安装手册」，也不是「配置手册」。**

### 必须有的五块

```
① 要开通什么       表：要开通/申请的东西 | 从哪步需要 | 要多久 | 花钱吗 | 能不能拖
                   ＋ 一句结论：动手前必须先搞定的是哪一样
② 逐个外部服务      每个服务三件事：怎么开通 / 要拿到什么（Key·地址·模型名）/ 要确认什么（权限·维度·上限）
③ 自检             能直接粘的验证命令（Key 用占位符，不引用环境变量）
                   ＋ 结果判读表：每个错误码对应什么原因
④ 高频坑           按踩到的概率排，每条一句症状 + 一句解法
⑤ 勾选清单         按阶段分组，标明「现在必须勾」与「阶段 N 前勾」
```

### 三条硬规则

1. **不给变量赋值**。写「API Key：`sk-` 开头一串，控制台只显示一次，当场抄下来」，不写 `XXX_API_KEY=sk-xxx`。变量怎么填是环境准备章的事，两章都写就会出现两份不一致的配置。
2. **不碰环境工具**。全篇不出现 Docker / uv / pnpm / Node 的安装步骤——出现一次，读者就会问「那到底该在哪一章装」。边界写在开头：本篇管账号与能力，环境准备管装。
3. **诚实处理专有标识**。原项目用的私有模型名、内部端点、特定套餐，要明确标「这是原项目当时的标识，你的账号里可能没有」，并给出退路（比如退化成通用模型名），说明退化后功能不受影响、只是失去某项优化。

### 什么时候可以不写

项目没有任何外部依赖（纯本地库、纯离线工具）时，**不要交一篇空壳**：在 `01-路线图.md` 开头写一句「本项目无外部服务依赖，跳过预先准备」，不建这个文件。

## 底线（目录怎么调整都不能丢）

1. **技术栈落到三个层次**：`02-技术栈/` 专章讲透（分层清单 + 精确版本 + 选型理由 + 官方入口）；每个步骤开头标注本步真正用到的技术；`03-实现开始/00-复现总指引/02-环境准备.md` 给出版本矩阵与安装命令，由 senior-engineer 校验可执行。缺一层视为交付不合格。
2. **每一步都有可执行的验证点**：`03-具体实现.md` 的每一步必须给出「看到什么算通过」，只给命令不给预期结果等于没给。
3. **导航与术语全书一致**：`README.md` 的章节导航表要能链到每一个文件；同一技术、同一概念在全书同名同写法。
4. **关键结论必须有溯源**：任何数字、版本、上限、契约、结论后面必须跟来源引用——拆有源码的项目写 `文件:行号`（如 `app/services/hybrid_search.py:142`），拆「素材重组型」项目写 `源素材文档#小节`。没有引用的关键结论一律视为不可信，`source-auditor` 会直接标记为「无溯源」。这条的用处是让读者能验证、让审计能机械执行，而不是凭手感查漏。
5. **面试与简历材料必须"答得上、核得实"**：每一条写进简历的表述、每一条面试答案，都要能在定稿正文里找到落点，并且你能在被追问三层时仍然答得出来。答不出来的技巧宁可不写——**这一章写错是有现实代价的**：它会被拿去投递、拿去面试，而技术章节写错只是读者多绕一步路。
6. **配图与正文必须同步，且正文能独立成立**：图是辅助，删掉图这一段还得读得通；正文一改，对应图必须跟着改。**所有结构类图一律手写 SVG**（分层、时序、状态机、ER、数据流、调用链），Mermaid 与字符画在本书里不存在，AI 生图只许用于不承担事实准确性的概念示意，**绝不用来画架构图与时序图**。另外，图全部是文件引用，路径一错全图就白——落盘后必须逐个点开验证。
7. **术语与归属先冻结，单篇有体量上限**：动笔前产出 `glossary.md`（每个概念一个正名 + `_Avoid_` 避用词）与 `ownership.md`（一段代码 / 一张表 / 一个口径只有一个 owner）。同一概念全书同名同写法；同一段代码不重贴，非 owner 章节写「本步增量 + 指路 + 本步的坑」。单篇 ≤ 600 行；600–900 行必须补「本章怎么读」导航表；> 900 行拆文件。细则见 `references/canon-and-glossary.md`。
