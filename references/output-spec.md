# 写作规范（output-spec）

交付物该长成的样子。目录层级与文件名可随项目调整，**唯一不变的判断标准**：读者能顺着目录一路读下去、跟着做出来，而且每一处都知道自己为什么在读它。

落盘目录：`<用户当前工作目录>/<项目名>-拆解教程/`

## 目录形态

```
<项目名>-拆解教程/
├── README.md                     总索引，导航链到每一个文件
├── 00-项目综述/
│   ├── 01-项目立意.md
│   └── 02-项目亮点.md
├── 01-整体架构/
│   ├── 01-架构总览.md
│   ├── 02-目录结构.md
│   ├── 03-具体模块.md            每模块一节；模块超过 8 个时拆成 03-具体模块/NN-<模块>.md
│   ├── 04-设计决策.md
│   └── 05-其他补充.md
├── 02-技术栈/
│   ├── 01-选择与决策.md
│   └── 02-环境安装.md
├── 03-具体实现/
│   ├── 00-项目准备/
│   │   ├── 01-外部服务.md        单篇，不套四件套
│   │   └── 02-搭建骨架.md        单篇，不套四件套
│   ├── 01-<能力主题>/
│   │   ├── 00-来龙去脉.md
│   │   ├── 01-亮点难点.md
│   │   ├── 02-功能流程与架构.md
│   │   └── 03-具体实现.md
│   └── NN-<能力主题>/ ...        按依赖顺序递增
├── 04-面试与简历/
│   ├── 01-项目陈述.md
│   ├── 02-简历写法.md
│   └── 03-面试问答.md            末节「高危追问」
└── assets/                       全部配图，按章节同名子目录
```

模块少、内容薄的项目可以合并层级（例如 `03-具体实现` 下主题合成一篇），但**四篇的分工不能丢**。

## 各目录写什么

| 位置 | 唯一要回答的问题 |
|---|---|
| `00-项目综述/01-项目立意` | 这个项目为什么存在：解决谁的什么问题，定位与边界 |
| `00-项目综述/02-项目亮点` | 它比同类好在哪：核心功能、解决了什么痛点 |
| `01-整体架构/01-架构总览` | 分几层、有哪些模块：一张地图 + 模块清单表 |
| `01-整体架构/02-目录结构` | 代码怎么摆：目录树 + 每个目录装什么 |
| `01-整体架构/03-具体模块` | 每个模块干什么、怎么跑：位置 + 输入 → 内部运作 → 输出 + 不负责什么 |
| `01-整体架构/04-设计决策` | 为什么这么设计：取舍、代价、放弃了什么 |
| `01-整体架构/05-其他补充` | 不属于上面四篇但有价值的横向参考 |
| `02-技术栈/01-选择与决策` | 用了哪些技术、精确版本、为什么选它、它落在哪个位置 |
| `02-技术栈/02-环境安装` | 怎么装出来：版本矩阵（技术 / 版本 / 安装命令 / 验证命令） |
| `03-具体实现/00-项目准备/01-外部服务` | 动手前要去控制台开通什么：账号、Key、额度、地域，以及能不能拖 |
| `03-具体实现/00-项目准备/02-搭建骨架` | 目录怎么搭：基础骨架建出来，一条命令验活 |
| `03-具体实现/NN-<主题>` | 这个能力怎么做出来（见下方四件套） |
| `04-面试与简历/*` | 怎么把这件事讲给别人听 |

## `01-具体模块.md` 的硬要求

**模块清单表在前，逐模块小节在后。** 清单列：模块 / 一句话职责 / 所在层 / 依赖谁 / 被谁依赖。读者先拿到索引，再决定深入哪个。

每个模块一节，固定四块：

```
## 模块 N：<模块名>

**位置**：属于哪层，谁调用它，它调用谁
**输入**：接收什么，从哪来
**内部运作**：按什么顺序处理，关键函数与数据结构（`文件:行号`）
**输出**：产出什么，给谁用
**不负责**：哪些事看起来归它、其实不归它
```

「不负责」这一块别省——它是防止读者把相邻模块职责算错的关键。

## `03-具体实现` 的切分与四件套

**按能力主题切，章序按依赖排。** 先做出能跑通的最小闭环，再逐个能力加上去；工程可维护性、可观测性这类横切主题，放在对应能力稳定之后。一个主题 = 一个实现步骤，不按文件目录切。

每个主题固定四篇，**四篇各只回答一个问题**：

| 篇 | 唯一问题 | 明确不写 |
|---|---|---|
| `00-来龙去脉.md` | 我们为什么走到这一步 | 不贴代码、不写实现细节、不重复讲全项目历史 |
| `01-亮点难点.md` | 这一步的取舍与卡点 | 不重写 `00` 的背景，不提前倒代码 |
| `02-功能流程与架构.md` | 这一步做了什么、怎么流转 | 不写「为什么做」（归 `00`）、不写命令与代码（归 `03`） |
| `03-具体实现.md` | 怎么动手、怎么算做成 | 不重新论证动机、不重画架构图 |

**承上启下是 `00` 的专属职责。** 它开头讲上一步留下什么、现在缺什么，结尾讲下一步接住什么；其余三篇开头只用一句话回指 `00` 的结论，不各自重写背景。

参考骨架：

```
00-来龙去脉.md
  ① 承上：上一步结束时是什么状态，留下哪个未解决的问题
  ② 现状：项目进展到哪，已有什么、还缺什么
  ③ 起因：为什么做这个能力（真实场景 / 不做会卡在哪，带溯源）
  ④ 目标：做完之后系统变成什么样，给一个可观察的完成画面
  ⑤ 阅读地图：四篇分别回答什么，带着哪个问题进 01
  ⑥ 启下：下一步会接住本步哪个产物

01-亮点难点.md
  ① 本步交付什么（只列产物）
  ② 关键取舍：选了什么、放弃了什么、代价是什么
  ③ 难点与亮点：一条一段，难点写清「卡在哪、怎么绕」
  ④ 前置概念扫盲：一句话定义 + 一个具体例子
  ⑤ 链路位置：指回 00 的阅读地图

02-功能流程与架构.md
  ① 本步改了哪些模块 / 文件
  ② 整体结构：本步用到的技术栈 + 结构图或管道图
  ③ 运行流程：一次调用端到端怎么走，含异常与降级分支
  ④ 关键设计决策与契约：决策 / 为什么 / 代价
  ⑤ 边界与交接：不做什么，指到 03

03-具体实现.md
  ① 环境前置（一句话回指 00，不重述）
  ② 实现步骤：命令 + 代码 + 真实文件路径，每个推进点前一句「为什么现在做这步」
  ③ 每步验证点：看到什么才算通过
  ④ 常见问题：只写本步专属的坑
  ⑤ 小结 + 下一步：接住 00 的启下
  ⑥ 驱动提示词原文（原项目由提示词驱动时才写）
```

附录编号只用一种风格：`### 附一 · …`、`### 附二 · …`，禁止「二、三、八、8.1」这种断档编号，也不要把附件条目写成 `##`。

## 叙述链三问

写完任意一个知识点或推进点，逐条自问。任何一问答不出就是断链，**补在它所属的那篇里**，不四处打补丁：

1. **从哪来**：依赖前面哪个结论 / 哪个文件 / 哪一步的产出？新名词就地给一句大白话定义。
2. **为什么现在**：为什么在这一步引入、不更早也不更晚？不做会卡在哪？因果有出处，查不到就写「推测，依据是⋯」。
3. **到哪去**：下一步怎么用它？本节结束前给一句「接下来我们会用⋯」，指向具体篇名。

## 语言尺度

**给初级程序员看，但不哄人。**

- 短句、主动语态，一个段落只推进一件事
- 术语首次出现给「一句话定义 + 一个具体例子」，之后直接使用
- 不写「显而易见」「简单来说就是」「你只需要」这类居高临下或虚假轻松的措辞
- 不把常识翻来覆去讲，也不靠降低信息密度换易读——**把因果讲清才是门槛低**
- 真实写出命令、版本、文件名与取舍代价

## 页型边界（防止各篇都以为自己该讲）

| 篇 | 该讲 | 不该讲 |
|---|---|---|
| 项目立意 | 动机、定位、边界 | 功能清单（归「项目亮点」） |
| 项目亮点 | 核心功能、解决的痛点 | 技术实现细节 |
| 架构总览 | 分几层、有哪些模块 | 单模块细节 |
| 目录结构 | 目录装什么 | 模块职责复述 |
| 具体模块 | 位置 / 输入 / 内部运作 / 输出 / 不负责 | 迭代历史、某一步怎么改的 |
| 设计决策 | 取舍与代价 | 功能复述 |
| 技术栈选择 | 版本、选型理由、作用位置 | 安装步骤（归「环境安装」） |
| 环境安装 | 版本矩阵 + 安装与验证命令 | 选型理由（归「选择与决策」） |
| 外部服务 | 只写要去控制台开通的东西 | 装环境、`.env` 怎么填 |
| 搭建骨架 | 建目录、验活 | 四件套那套难点分析 |
| 来龙去脉 | 承上启下、起因、目标、阅读地图 | 代码与实现细节 |
| 亮点难点 | 取舍与卡点 | 重写背景、提前倒代码 |
| 功能流程与架构 | 本步改了什么、怎么流转、契约边界 | 为什么做、命令与代码 |
| 具体实现 | 动手步骤 + 验证点 | 重新论证动机、重画架构图 |
| 面试与简历 | 从定稿提炼的表达 | 定稿里没有的技术点与数字 |

判定方法一句：**同一件事在两个地方都讲，只留最该讲它的那处，另一处写成一句「详见 X」。**

## `04-面试与简历/` 的三条取材铁律

1. **不套通用模板**：每个简历条目、每条面试答案的素材都要来自定稿正文。正文里没有的一个字都别加——面试官顺着问下去，编的那部分第一个塌。
2. **禁止冒领身份**：这份作品是**独立复现 + 架构拆解 + 技术写作**，不是「我开发了这个系统」。把复现说成开发，面试官追问两轮就穿帮——那是诚信问题，比技术答错严重。
3. **可核验**：能指向产物（教程目录 / 复现仓库 / 笔记）的就指向产物；「精通」「深刻理解」这类核验不了的形容词删掉，它们只会招来更狠的追问。

```
01-项目陈述.md
  ① 一句话版（20 秒）：是什么系统 + 解决什么问题 + 我做了什么
  ② 三分钟版：背景与目标 → 我实际做的事 → 挑一个难点讲透 → 收获与产物在哪
  ③ 十五分钟版：1-2 个模块的设计取舍，按「问题 → 方案 → 代价 → 怎么验证」展开

02-简历写法.md
  ① 项目条目（3-5 条：动作 + 技术 + 可验证的结果，末尾标素材出处）
  ② 技术关键词（只列真正动过手的，按熟悉度分档）
  ③ 规模数字（每个数字标明口径：自述 / 实测 / 文档声明）
  ④ 按岗位的改写版本
  ⑤ 明确不写的词（本项目没做过的事）

03-面试问答.md
  ① 高频问题表：| 问题 | 面试官真正在考察什么 | 答题骨架 | 素材出处 |
  ② 高危追问（末节）：| 追问 | 为什么会问到这里 | 你能诚实答到的上限 | 该怎么答 |
  ③ 四个必须诚实的地方：设计意图（只能推测）/ 线上故障（别编）/ 数字口径 / 团队角色
  ④ 反向提问清单
```

一条判断标准贯穿这三篇：**凡是写进去的，都要在被追问三层时仍然答得出来。** 答不出来的技巧宁可不要。

## 底线（目录怎么调都不能丢）

1. **技术栈落到三层**：`02-技术栈/01` 给选型与版本、`02` 给可安装的版本矩阵、每个实现主题开头标注本步用到的技术。
2. **每个实现主题都有可执行的验证点**：只给命令不给「看到什么算通过」，等于没给。
3. **每个模块讲清「输入 → 内部运作 → 输出」**，并写明它不负责什么。
4. **关键结论带溯源**：有源码写 `文件:行号`，素材重组型写 `源素材文档#小节`。没有引用的关键结论按不可信处理。
5. **导航与术语全书一致**：README 导航链到每个文件；同一概念全书同名同写法。
6. **配图与正文同步，正文能独立成立**：结构图只能手写 SVG；禁用 Mermaid、字符画、AI 生图代替结构图；图是文件引用，路径一错全图就白。
7. **术语与归属先冻结，单篇有体量上限**：动笔前产出 `glossary.md` 与 `ownership.md`；单篇 ≤ 600 行，600–900 行加「本章怎么读」导航表，> 900 行拆文件。
